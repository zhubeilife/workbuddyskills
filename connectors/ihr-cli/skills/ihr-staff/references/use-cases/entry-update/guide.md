# 编辑单条待入职资料

## 目标定义

修改或补全一条已存在的待入职记录，并保留用户没有要求修改的原值。完成标准是目标唯一、实际变化得到确认、更新成功且回读字段与确认内容一致。

本目标不修改花名册中的在职员工，也不审核入职登记表。

## 业务判断

读取[员工入职](../../domain/onboarding.md)和[待入职写入命令](../../commands/entry-write.md)：

1. 用户没有 `entryFormId` 时，先按姓名、手机号、部门或状态查询 `pending` 候选；多候选不能默认取第一条。
2. 使用唯一 ID 执行 `entry +get`，核对姓名、脱敏手机号、当前状态和用户目标。
3. 每次编辑必须执行 `entry +update-fields`。历史对话、其他租户 Meta 或字段中文名称不能替代本次字段规则。
4. 用当前详情作基线：
   - 未提及字段沿用旧值；
   - `readOnly=true` 或 `editable=false` 的字段拒绝修改；
   - 只有当前详情和用户输入都缺少的可编辑必填字段才追问；
   - 选项只提交本次规则返回的 `options[].value`；多匹配时请用户选择；
   - 只处理用户明确要维护的子集，不因可选空子集索取无关字段。
5. 规范化比较日期、空值、布尔值、选项值和多值顺序。没有实际变化时停止，不提交空更新。

之前读取的详情和字段规则可能在提交前发生变化，不能作为最终前置条件证明；`entry +update` 执行时必须重新校验目标 ID、当前状态、字段规则和重复更新。

## 执行与验证

1. 从详情业务对象与用户变化构造命令要求的完整 `payload`；不得把 CLI envelope、租户身份或认证信息放入载荷。当前契约不足以构造完整 payload 时停止。
2. dry-run 后展示目标 `entryFormId`、姓名和字段差异：未变化项标注“沿用原值”，变化项使用 `【已修改】字段：原值 -> 新值`；敏感值必须脱敏。
3. 用户确认该目标和差异后，使用完全相同的 payload 和精确匹配的 `confirm-entry-form-id` 执行一次。用户修改任何内容后必须重新生成差异并 dry-run。
4. 成功后重新执行 `entry +get`，逐项验证已修改字段；只读回读未反映变化时，不报告完成。

超时或响应不明时先回读详情：全部目标字段等于新值可报告“已通过回读确认”；仍为旧值可报告未生效；混合结果或读取失败时报告结果未知，不自动重试。
