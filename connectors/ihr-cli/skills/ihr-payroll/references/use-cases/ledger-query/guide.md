# Use Case：查询某期薪资台账

## 目标定义

在用户明确的台账名称或期间内，定位唯一 history/merge 台账，并按目标返回台账摘要、字段定义或当前页员工薪资明细。查询成功只代表当前权限范围内的当前命令结果，不代表全量工资分析或台账发布状态。

## 业务判断

1. 先区分用户要台账列表、字段定义还是员工明细；只要列表时不继续读取详情。
2. 识别名称、`year+month` 或完整日期范围。缺年份或台账对象存在多个合理解释时，询问一个最小澄清问题。
3. `salarySplit=true` 只是属性，仍按列表返回的 `ledgerType=history|merge` 处理。
4. 员工姓名、工号和部门名称是台账明细的服务端筛选条件，不解析为 staffId。
5. 工资总额、平均工资、split 子台账、导出和未公开字段不在本 Use Case 内。

## 执行与验证

1. 在[公开命令导航](../../domain/commands.md)定位 `ledger +list`，读取 Help 和[台账列表契约](../../commands/ledger-list.md)。
2. 只查询用户确认的一页。零候选如实说明；多候选按名称、年月、类型和状态请用户选择；唯一候选保存其完整上下文。
3. 用户只要字段定义时，定位 `ledger +detail` 并对同一上下文执行 `--fields-only`。返回 `ledger/fields` 才算完成。
4. 用户要明细时，先按 fields-only 把展示名解析为字段 code；再使用同一列表项的 history/merge 上下文、用户筛选和当前页执行详情。
5. 明细完成证据是结构化响应中的同一台账摘要、已选字段、分页信息和 `items`。只呈现用户已确认的字段和当前页，不复制整页原始 JSON。

## 停止条件

- 列表没有唯一可选台账，且用户没有提供区分信息；
- history/merge 上下文缺失、混来自不同列表项或类型与标识矛盾；
- 字段名称多候选、超过 50 个或契约无法解释；
- 用户要求自动翻页、全量金额统计、split、导出或 raw 接口；
- 鉴权、权限、业务、网络或响应解释失败。不得改查相邻台账或自动重试。
