# 公式处理流程

本流程把 Excel 公式、业务规则、表意公式或 code 公式收敛为可校验、可试算的薪资 code 公式。每个阶段有独立完成条件；后阶段不能反向证明前阶段正确。

## 1. 收集并解析输入

先确定源类型：

- Excel 公式：保留原公式，并取得每个单元格、列、命名区域与薪资项目名称或 code 的明确映射；相对行号只表示同一员工行时去掉行号，不能猜测跨行、汇总区或辅助表含义。
- 业务规则：把条件、比较、分支、引用项目、常量、空值和舍入要求逐项复述；任何会改变计算结果的歧义都先询问。
- 表意公式：字段以当前公司项目名称或引用服务名称表达。
- code 公式：字段已经使用薪资项目或引用服务 code 表达。

字段映射优先使用用户提供的项目名称；Agent 在内部把名称解析为唯一 code。保存模式可以从同一次最新模板 snapshot 按唯一 code 或完整名称解析；唯一模糊、包含匹配或数组顺序不能用于公式变量绑定。多个同名或零候选时展示项目名称、类型/类别名称和来源名称后询问，不要求用户复制 code。Excel 来源的目标先展示原公式作为来源；目标是复用项目或加入系统项目时，同时展示目标当前来源和当前公式状态，并提醒该模板内可以改为输入或修改公式。用户选择使用公式、修改公式或接受推荐公式时，先把 Excel 坐标、区域和表名替换为已确认薪资项目名称，生成薪资系统公式。后续确认与展示的公式正文必须是薪资系统公式，不得包含 Excel 单元格引用。

## 2. 翻译为薪资语言

读取 `ihr-payroll` 的 `references/commands/formula-language.md`，以其中的当前引擎语义为准。公式必须以 `=` 开头。

### Excel `VLOOKUP` 分支

检测到 Excel `VLOOKUP` 后，先展示并等待用户选择以下一种迁移方案：

- **表单内容转嵌套 `IF`**：使用用户提供的查找表逐行生成分支，保留 Excel 的精确/近似匹配模式、未命中结果和返回值类型。精确匹配使用 `=`；近似匹配仅在查找列排序及边界语义已确认时使用 `>`、`>=`、`<` 或 `<=`。不得用相邻单元格、缓存值或猜测的区间替代缺失表格内容。
- **智搭云表单转 `VLOOKUP`**：由用户先在智搭云建立对应表单，并明确查找键字段、返回字段和可供薪资公式引用的业务字段。公式翻译只处理接入后的字段引用；Excel 的工作表区域、单元格地址和外部工作簿引用不能直接作为薪资公式的 `table_array`。

两种方案都必须在用户选择后才进入 `TRANSLATE`。方案未选择、查找表未提供、智搭云字段未接入或 Excel 与薪资引擎存在未解决的匹配/未命中差异时，阶段状态保持 `needs_confirmation` 或 `BLOCKING`，不生成已完成的近似公式。方案选择只决定翻译路径，不授权创建智搭云表单或保存模板。

公式使用函数时，先读取 `ihr-payroll` 的 `references/commands/formula-functions.md`，执行一次 `payroll formula +functions`。只使用当前公司返回集合与静态语言参考的交集；函数名称存在不代表其签名或 Excel 行为相同。

逐项核对运算符优先级、空值、文本比较、日期、数组、舍入和函数签名。Excel 与薪资引擎无法等价表达时，列出具体语义差异和所需业务决定并停止；不得自行选择近似算法。

TRANSLATE 完成条件：生成一条以 `=` 开头的薪资系统候选公式，所有引用都有已确认名称/code，使用的函数在当前公司可用，且没有未确认的 Excel 语义差异。候选公式不得包含 A1/R1C1 坐标、工作表区域、外部工作簿引用或 Excel 专用引用。

Excel 公式列的用户确认必须落到以下一种结果：沿用目标项目当前设置、改为输入、或使用已确认的薪资系统公式。选择沿用或输入时，不需要生成新公式，但必须记录该决定；选择使用公式时，必须继续完成 VALIDATE 和 CALCULATE。

## 3. 校验并提取内部 code 公式

读取 `ihr-payroll` 的 `references/commands/formula-validate.md`。

公司模板编辑场景中，按前端逻辑把当前编辑器里的公式文本和同模板其他公式项目一起送入 `cirDependency`。当前编辑器公式使用薪资项目名称时，调用 `formula +validate` 传 `formulaFormat=IDEOGRAPHIC`；只有用户明确提供字段 code 公式时才传 `CODE`。同模板其他公式项目优先使用 snapshot / 页面数据里的表意公式元素拼接结果；只有确认它们已是 code 公式并且不含中文项目名时才使用 code 公式。

校验返回的 `exprItems` 是内部 code 公式的事实来源：保存和试算使用 CLI 成功结果中的 `codeFormula`；用户确认表展示当前编辑器里的薪资系统公式文本。不得调用独立转换命令，也不得把 Excel 单元格公式当作最终公式。

用户提供的 Excel 列映射先由 Agent 替换成已确认项目名称；校验失败、结果为空或返回字段与已确认映射冲突时停止。在 Windows/PowerShell 中，含中文项目名的公式输入优先使用 flags 或 UTF-8 `--json-file`，不要让默认管道直接承载这类 JSON，否则中文可能在 CLI 启动前被替换成 `?`，并被后端误报为非法操作符。若必须使用 PowerShell 5.1 的 `--stdin`，先执行 `$OutputEncoding = New-Object System.Text.UTF8Encoding $false`；仅设置 `[Console]::OutputEncoding` 不足。修正后必须用同一完整 JSON 重新执行 dry-run。

保存模式从最新 snapshot 收集同一模板除当前目标外、`source.id=FUNCTION` 且公式非空的项目，形成 `otherFields`。多个目标同时修改时，后一个目标校验使用本次已确认的新公式，未修改目标使用 snapshot 公式。输入项目不进入 `otherFields`。

只有 `validated=true` 表示语法、字段、函数和依赖校验通过；错误响应、问题元素或循环节点均阻断试算和保存。

校验完成条件：`validated=true`，且返回 `exprItems` 与 `codeFormula`。需要保存时同时保留当前编辑器公式文本和内部 code 公式。

## 4. 单字段试算

读取 `ihr-payroll` 的 `references/commands/formula-calc.md`。

保存模式使用目标项目当前 `valueMeta.roundingMode.id` 和 `valueMeta.pattern`；本 Use Case 不顺带修改进位设置。独立试算必须由用户明确提供进位规则和小数位。

样例字段 code 必须与最终公式引用一致。样例值来自用户或用户明确指定的数据，不生成工资、税额、日期或员工数据。一次只计算一个目标和一组样例；需要第二组样例时由用户明确提供并再次确认范围。

CALCULATE 完成条件：返回 `calculated=true` 和非空、非 `null` 结果，依赖数、进位规则和小数位与输入一致。保存前还必须由用户确认结果符合预期；仅有非空结果不能证明业务规则正确。
