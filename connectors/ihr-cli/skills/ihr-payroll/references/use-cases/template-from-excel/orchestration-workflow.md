# Excel 到薪资模板端到端流程

本流程连接 Payroll Domain 内五组处理阶段。各阶段的 Use Case Reference 是对应业务规则的唯一来源；本文件只定义阶段顺序、交接条件和跨阶段失效规则。

## 阶段

| 阶段 | 执行方 | 完成边界 |
| --- | --- | --- |
| `EXTRACT` | Excel 提取契约与 `ihr-cli base excel +extract` | manifest 完整、源哈希和全部计数通过校验 |
| `IDENTIFY` | 表格识别 Use Case | 唯一主表已自动或由用户选择，识别产物为 `complete` |
| `PROPOSE_FIELDS` | 薪资项目匹配 Use Case | 全部数据列已有已确认表头、唯一候选和完整设置提案，尚未写入 |
| `PLAN` | 本 Use Case | 一层分组、列顺序和每个 Excel 公式列的处理意向已确认 |
| `FINALIZE_FIELDS` | 薪资项目匹配 Use Case | 必要启用/创建明确成功，最终映射产物为 `complete` |
| `CREATE_TEMPLATE` | 公司模板配置 Use Case / CREATE，或[按名称定位已有公司模板](../../domain/company-template.md) | 空白模板创建成功，或已有模板完整名称精确匹配唯一 |
| `PREPARE_FORMULAS` | 公式编辑 Use Case | 所有选择使用公式的目标已完成校验、exprItems 已生成、非空试算且结果获确认；选择输入或沿用的 Excel 公式列已有明确决定；无公式时跳过 |
| `SAVE_RULES` | 公司模板配置 Use Case / RULES | 完整规则保存并读回 `verified=true`，或写入已发生后只读快照满足第二步业务不变量且仅有服务端隐藏元数据规范化差异 |
| `SAVE_ATTENDANCE` | 公司模板配置 Use Case / ATTENDANCE | 页面默认规则保存成功 |
| `COMPLETE` | 本 Use Case | 全部身份、数量和阶段产物状态通过最终自检 |

`PROPOSE_FIELDS` 阶段的 `companyTemplate +addable-fields` 与 `PREPARE_FORMULAS` 阶段的 `formula +validate` 都是 `CONFIRM_REQUIRED` 读取入口：`companyId`、`tenantId`、`Authorization`、`token` 不作为 CLI 输入，`other-fields-json` 只允许来自同一模板中已确认的公式上下文。

## 1. 建立身份链

新运行只把用户指定的工作簿作为源。按需读取 `ihr-base` 的 `base excel +extract` 契约并执行一次提取，记录源文件哈希、manifest 路径与哈希。后续阶段只传递已校验产物路径，不让下游再次从聊天中的列名、截图或摘要重建输入。

识别产物必须引用同一个 manifest 和源哈希；映射产物必须引用同一个识别产物、manifest、已选 `tableId` 和全量计数。每次读取阶段产物时计算文件哈希并与端到端产物核对。

首次 payroll 查询前确认当前登录公司属于用户本次目标范围。编排产物只记录环境和不可逆公司指纹；每次恢复和每个写阶段前重新计算，变化时停止，不把另一个公司的候选或写入结果接入原运行。

## 2. 写入前规划

薪资项目匹配阶段完成末级表头识别和候选查询后，在授权其启用或创建项目之前完成以下检查：

### 三张全量表

用户回复以三张完整 Markdown 表开头，再给出数量摘要和最小确认问题。三张表按“复用字段 / 加入系统项目 / 新建字段”分组；即使某组为空，也保留该表并注明“无项目”。产物路径放在表格之后，作为审计入口。每次用户确认或修改任一列后，重新生成并展示三张全量表；保留未变更列，不能只回显差异。

第一张表覆盖所有拟复用现有项目的列，固定为：

| Excel 列 | Excel 表头 | 复用薪资项目 | 当前状态 | 项目来源（公式/输入） | Excel公式处理 |
| --- | --- | --- | --- | --- | --- |

- `Excel 列` 使用主表列字母；`Excel 表头` 使用已识别的原始末级表头。
- `复用薪资项目` 使用当前公司候选的业务名称。字段 code、metaId、fieldId、公司/用户身份和其他内部标识留在产物绑定中。
- `当前状态` 显示“已确认复用”“待确认复用”或“启用后复用”。
- `项目来源（公式/输入）` 只显示“公式”或“输入”，不展示目标项目或 Excel 的公式正文，也不得显示“待 CREATE 后 RULES 快照读取”。模板 CREATE 前使用候选接口返回的来源判断；CREATE 成功后执行 `ihr-cli payroll companyTemplate +snapshot --payroll-config-id <ID>`，按项目 `code` 从 `rules.groupList[].fieldList[]` 和 `rules.noGroupSalaryFieldList[]` 读取 `source.id` 或 `valueMeta.formula` 校验状态。状态无法唯一确定时阻断。
- `Excel公式处理` 对没有 Excel 公式的列显示“无”；对有 Excel 公式的列显示“待确认：沿用目标设置 / 改为输入 / 转换Excel公式”。用户确认后显示“已确认沿用目标设置”“已确认输入”或确认后的薪资系统公式正文。

第二张表覆盖所有拟加入系统项目的列，固定为：

| Excel 列 | Excel 表头 | 系统项目 | 类别 | 类型 | 当前状态 | 是否公式 | Excel公式处理 |
| --- | --- | --- | --- | --- | --- | --- | --- |

- `系统项目` 使用未加入公司系统项目的业务名称；`类别`、`类型` 和 `当前状态` 只使用业务名称。`当前状态` 显示“已确认加入系统项目”或“待确认加入系统项目”。
- `是否公式` 只显示“公式”或“输入”，不展示系统项目公式正文。模板 CREATE 前使用系统项目候选接口返回的来源判断；CREATE 成功后使用同一次 `companyTemplate +snapshot`，按项目 `code` 读取 `source.id` 或 `valueMeta.formula` 校验状态。该列来自 Excel 公式时，仍必须进入统一的 Excel 公式处理确认。
- `Excel公式处理` 与复用字段表一致；Excel 公式列必须确认是否沿用系统项目默认设置、改为输入或改为转换后的薪资系统公式。

第三张表覆盖所有拟新建自定义项目的列，固定为：

| Excel 列 | Excel 表头 | 新建字段名称 | 类别 | 类型 | 属性摘要 | 当前状态 | 是否公式 | Excel公式处理 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

- `属性摘要` 至少包含进位规则、小数位、薪资档案引用、档案必填、强制使用、公司成本和固定取值来源“输入”；属性尚未选择时显示“待选择”。
- 对识别出可能由 Excel 公式驱动的自定义列，`是否公式` 在公式确认前显示“公式待确认”；没有公式显示“输入”。公式待确认列不得默认为输入或公式，必须交给后续公式阶段逐列确认。公式阶段先展示 Excel 原公式作为来源；用户选择使用公式、修改公式或接受推荐公式时，必须先转换为薪资系统公式，后续全量表的该单元格展示确认后的薪资系统公式正文。
- 自定义字段的 `当前状态` 显示“已确认新建”“待确认属性”或“公式待确认”。
- `Excel公式处理` 对没有 Excel 公式的列显示“无”；对有 Excel 公式的列显示“待确认：改为输入 / 转换Excel公式”。用户确认后显示“已确认输入”或确认后的薪资系统公式正文。

三张表均按 Excel 列顺序排列，任何列只能出现在其中一张表中。拥有多个当前公司复用候选的列仍放在“复用字段”表中，`复用薪资项目` 单元格列出全部候选并标记“待确认复用”；不能另起混合表。复用字段的“项目来源（公式/输入）”列和加入系统项目的“是否公式”列只展示目标状态，不展示公式正文；“Excel公式处理”列展示 Excel 公式列的待确认或已确认处理结果。Excel 原公式只在公式确认阶段作为来源展示，不复制进编排产物，也不能作为用户确认后的公式正文。
- 表内确认后的公式只用于本次用户核对；端到端产物继续只保存公式状态、数量、哈希和阶段产物引用。
- 表格之后仅询问会改变映射结果的问题。用户确认前保持 `PROPOSE_FIELDS`；用户每次回复后必须先更新三张全量表，再提出下一组最小确认问题。

### 写入确认摘要

每个 dry-run 和写入结果给用户展示业务摘要，不展示技术执行摘要。业务摘要只包含阶段、动作、项目名称、数量、用户已确认的关键设置、dry-run 是否通过、实际写入是否完成和只读回查是否通过。确认问题使用业务语言，例如“确认创建以上 26 个薪资项目？”。

以下内容只保存到对应阶段产物、日志或内部校验，不默认主动展示：`success=true`、HTTP method、接口路径、`apiPath`、request target、headers、profile、raw JSON payload、payload SHA、字段 code、metaId、fieldId、接口返回的内部结构和源码/接口实现名称。仅在用户明确要求技术明细，或哈希不一致、写入未知、回查不一致等需要解释阻断原因时，才展示最小必要技术信息。

写入前仍必须持久化或可重建同一规范化 payload，并在内部校验 dry-run 和实际写入输入一致；一致性证据进入产物，不作为普通确认文案的一部分。

1. 模板名称非空，且不是从文件名、工作表名或单元格推断的名称；确认视图使用业务名称，不展示内部 code。
2. 全部数据列已有确认表头和拟定的唯一目标；每个 CUSTOM 项都已由薪资项目匹配 Use Case 主动完成类别到类型及其余可配置属性的联动选择，公司成本已从字段类型 `companycostop` 派生。任一向导未完成时保持 `PROPOSE_FIELDS`，继续展示当前一级的有效选项，不进入字段写入或模板规划。
3. 分组方案覆盖全部 `excelColumnId`，同一列只出现一次：
   - `groupPath` 为空的列进入未分组列表；
   - 只有一层上级表头时，建议使用该原始名称作为模板分组；
   - 多层路径无法直接映射到单层模板分组时，展示完整路径并请用户为每条路径指定一个分组名称；不自行拼接、截断或选层级；
   - 分组按首次出现列排序，组内和未分组项目按 Excel 列顺序排列。
4. 扫描已选主表 `dataRange` 内的公式，按目标 `excelColumnId` 分类。只要主表列存在 Excel 公式，该列就是公式确认目标，和最终映射为复用字段、加入系统项目或新建字段无关：
   - 没有公式单元格的是输入目标；
   - 同一列公式在仅消除同员工行号后仍保持同一结构，才可提出一个公式目标；
   - 公式与手工值混合、存在多个结构、跨行/汇总引用、辅助表或外部工作簿引用时，列出差异并请用户决定规范公式或明确改为输入目标；
   - 公式引用的每个本表列必须能落到本次唯一字段映射；其余业务概念由用户补充，不能用相邻列、同名候选或样例值猜测。

用户确认表头、映射、分组和公式分类后，才进入薪资项目匹配 Use Case 的写入确认。所有 Excel 公式列必须至少取得公式处理意向确认；需要转换为薪资系统公式的列可在取得项目 code 后完成转换、校验和试算。字段启用与批量创建仍是两个独立写阶段。成功后使用最终返回的 code/metaId 更新内部计划；对用户只展示业务名称和回查结果，后续失败不回滚这些公司项目。

## 3. 创建模板并准备公式

FINALIZE_FIELDS 完成后再次核对映射产物和公司指纹。把模板名称、固定空白来源、完整分组计划和公式目标清单交给公司模板配置 Use Case。复用已有公司模板时按[按名称定位已有公司模板](../../domain/company-template.md)绑定并跳过 CREATE；否则只完成 CREATE。CREATE 的 dry-run 和确认以对应 Guide 为准，成功后记录同一个 `payrollConfigId`。CREATE 前三张确认表均只显示候选接口确定的公式状态；不得用 Excel 原公式替代复用字段或系统项目的状态。

随后进入公司模板配置 Use Case 的 RULES 读取阶段，取得最新 snapshot 与 `addable-fields --for-rules` 的目标 `ruleField`，按 `code` 从 snapshot 的 `rules` 校验复用字段和加入系统项目的“公式/输入”状态，并更新新建字段的公式状态，再重新展示三张全量确认表；这次刷新不是保存确认。快照读取失败、项目集合不完整或公式状态无法确定时停止，不得退回 Excel 原公式。所有 Excel 公式列的公式处理状态仍由用户确认决定。每个计划项目必须按 mapping 中的稳定 metaId/code 在候选中唯一解析；名称只作为无 ID/code 时的唯一精确备选。

有公式目标时，把以下信息交给公式编辑 Use Case：

- 目标列对应的字段 code/名称；
- 每一个 Excel 公式列：Excel 原公式、目标项目当前来源/公式状态、用户确认的列到字段映射；选择转换时，同时提供待转换的薪资项目名称公式；
- 复用字段和加入系统项目默认不覆盖目标项目设置，但仍必须询问用户是否需要修改；用户选择修改时，允许把目标改为输入，或把 Excel 公式转换为薪资系统公式后作为该模板中的公式；
- 同批其他公式目标，用于循环依赖校验；
- RULES 候选中的目标进位规则和小数位；
- 用户提供的样例值，或用户明确授权使用的一个 Excel 数据行。

公式编辑阶段只完成校验和试算，不执行自己的保存分支。每个 Excel 公式列都先显示 Excel 原公式；用户确认、修改或接受推荐后，确认对象必须是当前编辑器中的薪资系统公式文本或明确的“输入/沿用目标设置”，不能是 Excel 单元格公式。校验返回的 `exprItems` 作为内部 code 公式来源，按前端逻辑拼接后再进入试算和保存。选择使用薪资系统公式的目标必须逐项满足 `validated=true`、试算结果非空且用户确认结果符合预期后，才能生成公式处理完成产物；展示确认后的项目名称公式正文，同时显示项目名称、依赖名称、公式格式名称、进位规则名称和结果。选择输入或沿用目标设置的列记录最终决定，不生成新公式。原始样例值不进入端到端产物；未明确授权的员工行不能用于试算。

没有公式目标时把 `PREPARE_FORMULAS` 标为 `SKIPPED`。用户明确把某个 Excel 公式列改为输入目标时记录该决定，该列不得再携带从 Excel 推导的模板公式。

## 4. 保存模板后两步

把完整分组计划、全部最终映射项目和已准备公式配置交给公司模板配置 Use Case。已准备公式配置可以覆盖本模板内任一已确认目标的来源和公式，包括复用字段、加入系统项目和新建字段；未被用户确认为修改目标的项目保持目标当前设置。RULES 必须以最新 snapshot 为基线；若公式准备期间 snapshot 变化，重新读取 RULES 上下文，并重新校验受影响公式和试算设置。

公司模板配置 Use Case 生成全量 RULES dry-run 后，展示模板名称、分组/项目名称、输入/公式数量及明确删除项，取得独立确认并只保存一次。只有读回 `verified=true` 且项目集合、顺序和公式目标与计划一致时进入 ATTENDANCE。若保存命令提示写入已发生但严格读回比较失败，执行一次只读 snapshot；当项目集合、顺序、公式/输入来源、用户确认公式和统计均与计划一致，且差异只落在 `company-template-save-rules.md` 命令 Reference 定义的“可忽略隐藏元数据”白名单时，仍可进入 ATTENDANCE。其他读回差异必须停止。

ATTENDANCE 固定保存页面当前默认规则。完成其独立 dry-run 和确认后只执行一次。确认只显示模板名称和“页面当前默认值”；只有返回 `saved=true`、`savedCount=1`、同一个模板 ID 和 `settingsSource=PAGE_DEFAULTS` 才进入最终自检。

## 5. 恢复与失效

- 源文件、manifest、识别选择或映射身份变化：回到最早变化的阶段，废弃所有下游确认。
- 当前公司指纹变化：停止；原公司的 payroll 结果不能在新公司继续使用。
- 模板已经 CREATE 成功：恢复时保留 ID，不再次创建；名称变更需用户决定继续原模板还是终止本运行，本 Use Case 不改名或删除。
- 公式、分组、项目集合或 snapshot 变化：重新生成受影响的公式确认或 RULES dry-run；不复用旧 payload 确认。
- 任一写入返回未知：端到端状态为 `unknown`，按对应 Guide 只读核对后等待用户决定；不能自动重试或推进。
- RULES 保存返回引用尚未加入当前薪资表：读取[补齐公式引用项目](../company-template-configure/missing-formula-reference.md)。
- 后续失败留下的已启用/新建公司项目或空白模板属于已发生副作用。产物记录它们并提供恢复入口，不执行补偿删除。

## 生产可用证据

本 Use Case 只能依赖已加载的 Domain/Use Case Reference、具体命令 Help、受控命令 dry-run/执行结果和只读回查来确定下一步。现有契约未写明必要输入或恢复规则时，先停止并暴露契约缺口；补充相应契约后再继续。

## 交接自检

1. 每个阶段产物路径存在、哈希一致、Schema 受支持，且没有被覆盖。
2. `columns`、布局列和模板字段一一对应；数量、顺序、唯一性一致。
3. 每个公式目标都引用本次最终字段 code，且有公式编辑 Use Case 的通过证据；输入目标没有意外公式配置。
4. 所有写入确认都晚于对应 dry-run，且 payload 哈希一致。
5. 模板创建、RULES 和 ATTENDANCE 始终使用同一 ID；已成功阶段没有重复执行。
6. 最终产物不含员工行、薪资样例、完整公式、token、公司 ID 或用户 ID。
