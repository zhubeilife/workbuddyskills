# 表头确认与薪资项目匹配规则

## 末级表头

只处理已选薪资主表的列，不把辅助表列带入映射。

1. 使用合并单元格、连续表头行、数据起始行、样式边界和列数据形态确定表头层级。不能只取第一行非空文本。
2. 合并表头覆盖的文本向其跨度内传播为分组路径；最靠近数据区域、实际标识该列业务含义的非空节点是末级表头。
3. 上层节点只形成 `groupPath`，不创建公司薪资项目。姓名、部门、考勤、收入、补贴、扣款和统计列的末级节点都参与项目映射。
4. `excelColumnId` 固定为 `sheet-<三位序号>:col:<大写列字母>`，例如 `sheet-001:col:D`。列移动、工作表变化或源哈希变化都产生新的输入版本，不能沿用旧映射。
5. 保存原始末级名称、规范化名称、完整分组路径、顺序、表头单元格和问题 code。用户确认视图按来源展示公式：复用字段和加入系统项目的项目来源只展示公式状态；任一 Excel 公式列都展示公式处理状态。进入公式确认阶段后先展示 Excel 原公式作为来源；用户选择公式路径后展示已转换的薪资系统公式正文，选择输入或沿用时展示已确认的最终决定。映射产物仍只保存公式状态、数量、哈希和阶段产物引用，不写入员工数据值或完整公式。

### 公式正文来源与刷新时机

- `salaryField +list` 和 `salaryField +detail` 的公开结果只用于项目元数据匹配。复用字段和加入系统项目的项目来源列只记录是否为公式，不展示正文。
- 模板 CREATE 前尚无 `payrollConfigId` 时，复用字段和加入系统项目表的项目来源显示候选接口返回的“公式/输入”；新建字段表显示“公式待确认/输入”等状态。Excel 原公式不在字段匹配表展示，交由后续公式确认阶段展示。
- 模板 CREATE 成功后必须调用 `ihr-cli payroll companyTemplate +snapshot --payroll-config-id <ID>`。在 `rules.groupList[].fieldList[]` 与 `rules.noGroupSalaryFieldList[]` 中按项目 `code` 建索引，据 `source.id` 和 `valueMeta.formula` 更新复用字段、加入系统项目和新建字段的公式状态。复用目标明确为公式但快照没有非空公式时阻断并要求重新读取/处理；新建字段在公式确认前允许保持待确认状态。
- 公式确认阶段处理所有 Excel 公式列，不按映射类型过滤。先展示 Excel 原公式、目标项目当前来源和当前公式状态；对复用字段和加入系统项目，提醒用户可沿用目标设置、改为输入，或改为转换后的薪资系统公式。用户选择使用公式、修改公式或接受推荐公式时，必须先转换为薪资系统公式，后续展示已确认的薪资系统公式正文；用户选择输入或沿用时展示该最终决定。之后用户每次确认或修改任一映射、项目属性或公式决定，都先按最新确认状态重算并重新展示三张全量表；快照或项目集合变化时重新读取并使旧确认失效。

以下问题必须由用户解决：

- `MISSING_LEAF_HEADER`：数据列没有可确定的末级表头；
- `DUPLICATE_LEAF_HEADER`：多个列的末级名称相同，且用户尚未确认不同标准名称或明确复用例外；
- `AMBIGUOUS_HEADER_LEVEL`：两个或以上层级都可能是末级；
- `HEADER_DATA_MISALIGNMENT`：表头跨度与数据列无法稳定对齐；
- `DUPLICATE_MAPPING_TARGET`：两个列将复用同一个公司项目。

## 名称规范化

规范化只用于生成候选，不替换用户可见原名：

1. Unicode 兼容归一化和全角/半角统一；
2. 去除首尾空白，把连续内部空白折叠为一个；
3. 统一常见括号及标点形式；
4. 比较时可忽略不改变业务含义的分隔符，但不能删除“应发/实发”“税前/税后”“个人/公司”“补发/补扣”等限定词；
5. 同义词和语义相似只产生候选，不自动改名。

## 匹配顺序

对每个列依次查找，命中后仍保留证据和候选集：

1. `EXACT_NAME`：原始或已确认标准名称与当前公司项目完全相同；
2. `NORMALIZED_NAME`：规范化后完全相同；
3. `SYSTEM_ALIAS`：系统候选提供的别名、code 语义或维护的同义关系一致；
4. `SEMANTIC_SIMILAR`：结合分组、相邻列、样例类型、数字格式和公式存在性得到的语义推荐。

完全同名应只有一个当前公司候选；若返回多个，记录 `DUPLICATE_SYSTEM_STATE` 并阻断。语义候选不论有效或失效、置信度多高，都不能自动成为最终映射。

候选展示按三张表分组：复用字段、加入系统项目、新建字段。每次都输出三张表，即使某组为空也保留表头并注明“无项目”。每张表都包含该组全部列，不把三类项目混在一张表中。展示名称、类别/类型、来源、推荐原因、当前确认状态和适用的公式信息；复用字段和加入系统项目的项目来源只显示公式状态，三类项目都显示 Excel 公式处理状态，确认后显示薪资系统公式正文或“输入/沿用目标设置”的最终决定。内部 ID/code 只保存在产物和命令输入，不要求用户手工提供。

## 用户可见写入摘要

字段启用、系统项目加入和自定义项目创建的 dry-run/执行结果，默认只向用户展示业务信息：

- 动作：启用失效项目、加入系统项目或新建自定义项目；
- 数量：总数及按动作/类型拆分的数量；
- 项目：薪资项目名称，以及 CUSTOM 的类别、类型、进位、小数位、薪资档案引用、档案必填、强制使用和派生公司成本；
- 状态：dry-run 已通过、已写入、只读回查已通过或阻断原因。

普通确认文案不展示 `success=true`、HTTP method、接口路径、`apiPath`、headers、profile、raw payload、payload SHA、内部 code/ID、接口返回内部结构或源码/实现名称。payload 哈希仍必须写入产物并用于实际写入前后一致性校验；只有用户要求技术细节，或出现哈希不一致、写入未知、回查不一致时，才展示最小必要技术字段。

## 当前公司候选状态

在决定复用或新建前，用标准名称查询 `salaryField +list`，并省略 `valid` 筛选，让一次查询同时覆盖有效和失效项目。列表接口的名称条件是包含匹配；返回项仍按精确、规范化、别名和语义顺序分类，不能把包含命中直接当作同名或自动复用。

- 精确同名且 `valid=true`：作为当前公司复用候选，不再创建同名项目；
- 精确同名且 `valid=false`：作为“启用后复用”的首选候选，记录 `INACTIVE_COMPANY_FIELD_CONFIRMATION_REQUIRED` 并询问用户是否恢复为有效；用户拒绝时仍禁止同名创建，只能改标准名称或选择其他目标；
- 规范化、别名或语义候选且 `valid=false`：与有效语义候选一同展示，但明确标记“确认后需要先启用”；用户拒绝不会阻止使用原标准名称新建，除非另有精确同名失效项；
- 精确同名返回多项：记录 `DUPLICATE_SYSTEM_STATE`；
- 当前页没有精确同名但仍有后续页：记录 `COMPANY_FIELD_LOOKUP_INCOMPLETE`，取得后续页明确结果前不进入新建清单；
- 用户修改标准名称或 CUSTOM `fieldName`：对新名称重新执行同样的无状态筛选查询，旧查询结果不再作为创建依据。

把查询返回的 `metaId/name/valid/source/categoryCode/typeCode` 保存为候选证据。失效项目在批量启用并读回 `valid=true` 前不能写入最终复用映射。

## CUSTOM 创建前候选闭环

本轮候选查询完成后建立三个精确名称索引：`addableByName` 来自 `companyTemplate +addable-fields`，`companyFieldByName` 来自省略 `valid` 的 `salaryField +list` 全状态补查，`systemNotAddedByName` 来自 `salaryField +system-not-added --scope all`。索引只按返回项的 `name` 精确匹配，不用包含命中代替精确命中。

对每个标准名称按以下闭环落点处理：

1. 命中 `addableByName` 或有效公司项目时，落点为“复用字段”；多项命中则作为复用多候选等待确认。
2. 仅命中失效公司项目时，落点为“启用后复用”确认；用户拒绝启用时，先改名并重新补查候选。
3. 命中 `systemNotAddedByName` 时，落点为“加入系统项目”；多项命中则等待确认。
4. 三个精确索引都未命中、候选页完整且没有已接受复用候选时，才允许进入 CUSTOM 属性向导。

如果 `salaryField +batch-create` 返回“提供字段重名/请选择提供字段”语义，按候选闭环失效处理：刷新 `addable-fields`、对应名称的 `salaryField +list` 和 `system-not-added --scope all`，以最新命中项重新归类为复用或加入系统项目；原 CUSTOM payload 失效，新的 dry-run 必须基于重新分类后的决定生成。

## 新建薪资项目名称强校验

拟新建 CUSTOM 项目前，先对用户确认的 `fieldName` 做名称强校验。以本节规则和 `salaryField +create` / `+batch-create` 的本地 normalize 为准。

- 通过：进入自定义项目属性向导。
- 未通过：该列保持 `needs_confirmation`，询问新的合规名称。
- 用户修改名称后：重新执行当前公司候选补查和系统候选匹配，旧候选与旧确认失效。

有效名称必须同时满足：

- 长度 1..100 个字符；
- 不含空白（半角空格、全角空格、制表符、换行）；
- 不全为数字；
- 字符仅限中文、英文字母、数字、下划线，以及越南文、柬埔寨文、泰文。

Excel 推断出的默认名称也走同一校验。不合规时展示原因并请用户给出合规业务名称；保留原名，不删改字符后继续创建。

## 失效候选启用

用户确认一个或多个失效候选后：

1. 按候选顺序生成唯一 `metaIds[]`，保存每个 metaId 到 `excelColumnId` 的绑定；
2. 使用同一 payload 执行 `salaryField +batch-enable --stdin --dry-run`，按“用户可见写入摘要”展示项目名称和影响数量后取得写入确认；
3. 只执行一次批量启用。命令会读取完整项目设置、只修改有效状态并读回；
4. 全部读回为有效后，把这些列更新为 `REUSE`；部分失败或结果不确定时保持 `UNRESOLVED`，停止后续创建；
5. 用户修改启用集合后生成新的 payload、哈希和 dry-run，旧确认失效。

## 自定义项目属性向导

只有当前公司候选状态补查完整、三个精确名称索引均未命中、没有被接受的复用候选、没有阻止同名创建的失效精确同名项，且未加入系统项目也没有被用户接受时，才进入 CUSTOM 属性向导。先执行一次 `salaryField +create-options`，把本轮返回值作为该版提案的选项快照；查询失败或选项名称缺失时停止，不使用缓存、页面默认值或 code 补齐。

对每个拟新建项目主动完成以下步骤。每一步先展示当前可选项的业务名称，再请用户选择；不要等用户主动追问有哪些选项，也不要把推荐值当成已选值。

1. **所属类别**：从可选类型反向得到类别集合，只展示至少包含一个 `customizable=true` 且 `hidden!=true` 类型的类别。字段类型是否可选以类型自身属性为准，不使用类别的 `customizable` 过滤。类别选择完成后，立即进入字段类型选择。
2. **字段类型**：只展示 `categoryCode` 属于已选类别、`customizable=true` 且 `hidden!=true` 的类型。展示类型名称，不展示类型或类别 code。
3. **进位规则**：展示本轮 `roundingModes[]` 的全部名称并请用户选择。
4. **小数位**：说明允许范围为 `0..8`，结合整列有效数据的数字格式和精度提供推荐，再请用户明确选择一个整数。
5. **派生公司成本**：直接读取所选类型由 `salaryFieldTypes/search` 返回的 `companycostop`。保存其 `id`，使用其 `title` 或本轮 `companyCostOperations[]` 的对应名称展示“由字段类型确定：<名称>”。创建请求必须显式提交 `companySalaryField.companyCostNumOp.id`，无法解析公司成本操作时停止生成完整提案；该属性是派生结果，不向用户提供选项，也不要求用户另选加项或减项。
6. **薪资档案引用**：所选类型内部绑定为 `salary`、`pretaxallowance` 或 `text` 时展示“是/否”；其他类型只展示并请用户确认“否（所选类型不支持）”。
7. **档案必填**：薪资档案引用为“是”时展示“是/否”；引用为“否”时只展示并请用户确认“否”。不得形成“档案必填=是、薪资档案引用=否”的组合。
8. **强制使用**：展示“是/否”。用户选择“是”前，明确说明该项目会影响新建及历史薪资模板。
9. **固定属性**：展示取值来源固定为“输入”，备注固定为空；这两项只作说明，不让用户选择，也不写入 Excel 公式。

每个需要用户选择的枚举步骤使用“选项名称、是否推荐、推荐理由”的可见结构。可以结合项目名称、原始末级表头、分组路径、相邻列、整列数据类型与数字格式、公式存在性提出一个推荐值并排在首位；推荐值必须属于当前可选集合，理由必须指向实际证据。证据不足时不推荐。不得在理由中展示员工薪资值，不得只根据单行样例判断类型或小数位。公司成本不参与推荐，因为其值完全由字段类型决定。

## 批量创建请求与确认

生成 `salaryField +batch-create` payload 时只使用本 Use Case 已确认的映射决定、Payroll 的 batch-create Reference、具体命令 Help、dry-run 和只读回查；必要字段或恢复规则没有公开契约时停止并要求先补齐命令契约。

请求构造遵循 `ihr-payroll` 的 `references/commands/salary-field-batch-create.md`：

写入请求前先执行闭环审计：取所有 `decision=CUSTOM` 的 `fieldName`，与本轮 `addableByName`、`companyFieldByName`、`systemNotAddedByName` 做交集。交集非空时该映射版本无效，下一步是回到候选确认并重新展示三张全量表；dry-run 只基于审计通过的版本生成。

1. SYSTEM 项按 Excel 列顺序取本轮 `salaryField +system-not-added` 的完整选中对象，逐项交给 `salaryField +add-system` 的 normalizer，再放入 `createSysFieldInfos`；系统对象的业务属性保持不变。
2. CUSTOM 项使用 batch-create reference 中的单项创建结构；CLI 会重建 `salaryField +create` 的扁平输入并复用其 normalizer。`fieldName` 必须已通过强校验，`source` 和 `usingStaffSalarySource` 固定为输入，`formula` 固定为空字符串，`remark` 固定为空字符串。请求字段使用后端公开字段名 `forcedTouse`；产物和用户展示可继续使用业务名称“强制使用”。
3. `companySalaryField.companyCostNumOp.id`、`valueMeta.roundingMode.id`、`valueMeta.pattern`、`useInStaffSalary`、`forcedTouse` 和 `required` 必须显式提供，并接受 `salaryField +create` 的同一套范围和依赖校验。
4. `requestIndex -> excelColumnId` 绑定必须在 dry-run 前持久化。dry-run 通过后，用“用户可见写入摘要”展示拟创建/加入项目和数量，取得独立确认；实际写入前内部校验 payload 哈希一致，不把哈希放入普通确认文案。
5. 写入成功后按响应顺序回填结果，再用只读查询验证项目可用于当前公司；对用户展示创建成功数量和三张全量确认表，不展示内部 ID/code。

## 确认视图与公式展示

确认视图固定输出三张完整表，顺序为“复用字段”“加入系统项目”“新建字段”；某组为空时仍输出该表及“无项目”说明。每次用户对任一项目作出确认或修改后，先重新计算全部列的当前决定、公式状态和属性，再重新展示三张全量表；保留没有变化的列，不能只展示差异。

- 复用字段：项目来源只显示“公式”或“输入”。CREATE 前用候选接口返回的来源判断；CREATE 后从 `companyTemplate +snapshot` 的 `rules.*.fieldList[].source.id` 与 `valueMeta.formula` 校验。不得显示“待 CREATE 后 RULES 快照读取”，也不得用 Excel 原公式替代。
- 加入系统项目：项目来源只显示“公式”或“输入”状态，不展示系统项目公式正文。CREATE 前用系统候选接口返回的来源判断；CREATE 后从同一次 snapshot 校验。
- 新建字段：完整展示类别、类型、进位、小数位、薪资档案引用、档案必填、强制使用、派生公司成本和固定取值来源；项目来源在确认前只显示“公式待确认”或“输入”。
- Excel 公式处理：任一列在 Excel 主表数据区存在公式时，不论其映射为复用字段、加入系统项目或新建字段，都显示“Excel公式待确认”。进入公式确认阶段后逐列展示 Excel 原公式作为来源；用户选择使用公式、修改公式或接受推荐公式时，必须先转换为薪资系统公式，再在该列展示确认后的薪资系统公式正文。用户选择改为输入或沿用目标设置时，在该列展示对应最终决定。

用户确认视图的三张表按 Excel 列顺序排列且互斥完备，表后只提出仍会改变决定的最小问题。复用字段和加入系统项目的项目来源只展示公式状态；所有 Excel 公式列都必须有公式处理意向确认。Excel 原公式只在公式确认阶段作为来源展示，不写入映射产物；标记“Excel公式待确认”时，必须先逐列确认最终处理方式，才能进入本 Use Case 的启用或创建写入确认。

联动选择遵循以下失效规则：

- 用户重新选择所属类别时，原字段类型及其后的全部选择失效；立即重新过滤并展示新类别下的类型。
- 用户重新选择字段类型时，类型后的全部选择失效；立即读取新类型的 `companycostop` 更新公司成本展示，并重新计算进位规则、小数位和布尔属性推荐。
- 用户把薪资档案引用从“是”改为“否”时，原档案必填选择失效，并立即把唯一可选值“否”展示给用户确认。
- 本轮 `create-options` 结果变化、用户修改项目名称或列证据变化时，重新计算受影响的推荐；候选集合变化时废弃对应选择。

一次属性向导只在以下信息齐全后完成：已通过强校验的项目名称；本轮选项中相互匹配的类别和类型；已选择的进位规则、小数位、薪资档案引用、档案必填和强制使用；与所选类型 `companycostop` 完全一致的派生公司成本；固定“输入”来源及空备注说明。内部 code 只保存为所选名称的唯一绑定。多个 CUSTOM 项分别保存向导状态，任何一个未完成时保持 `needs_confirmation`。

## 完整确认

确认视图至少包含每个列的：列位置、原始末级名称、标准名称、分组路径、最终决定（复用/启用后复用/系统创建/CUSTOM）、目标名称、当前有效状态，以及 CUSTOM 的全部设置。任何被省略的列都视为未确认。

用户确认后检查：

1. 列标识集合与主表实际数据列集合一致；
2. 默认没有重复目标项目；
3. 所有候选歧义和 header issue 已解决；
4. CUSTOM 名称全部通过强校验，设置无空缺，并仍存在于最新元数据结果；
5. CUSTOM 名称与本轮 `addableByName`、`companyFieldByName`、`systemNotAddedByName` 均无精确交集；
6. SYSTEM 项保留同一轮 system-not-added 完整对象且 code 未变；
7. 当前公司项目列表、上游哈希或用户决定变化时，旧确认失效。
8. 启用后复用项的 metaId、名称和失效状态仍与本轮查询一致。

## 用户展示名称

候选确认只展示 Excel 末级表头、薪资项目名称、分组名称、类别名称、类型名称、来源名称、计税类型名称、有效状态、推荐原因，以及按列决定展示的公式信息：复用字段和加入系统项目的项目来源只展示公式状态；所有 Excel 公式列都展示公式处理状态。进入公式确认阶段后展示 Excel 原公式作为来源；用户选择使用公式、修改公式或接受推荐公式后，展示已转换的薪资系统公式正文，用户选择输入或沿用目标设置时展示该最终决定。`excelColumnId`、metaId、fieldId、项目 code、`decision`、`activation` 及 issue code 只保存在产物和命令输入中；向用户说明决定时使用“复用现有项目/加入系统项目/新建自定义项目/待处理”和“有效/失效/启用后复用”。CUSTOM 设置的类型、类别和进位使用本轮选项接口返回的名称；公司成本只展示所选类型 `companycostop` 派生的名称或“不计入公司成本”。
