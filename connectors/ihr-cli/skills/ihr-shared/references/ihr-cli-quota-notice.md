# 租户月度额度

智能体调用 i人事的次数按**当前公司、自然月**限额。查询入口是框架命令 `ihr-cli tenant quota`，不要为此去 grep `--help`，也不要新建业务 Domain。

## 查询

用户问「额度还剩多少 / 本月调用了几次 / 智能体额度」时，直接执行：

```bash
ihr-cli tenant quota
```

该命令只读，不消耗公司额度。向用户只解释公司本月 `limit` / `used` / `remaining`，不要展示或对比本地计数。

`tenant quota` 只能响应用户明确的额度查询，不能作为任何业务命令的前置检查。业务执行前不要读取额度、比较预计调用次数与剩余额度或据此停止；只有实际业务调用返回 HTTP 429 后，才进入下方的错误提示流程。

不要把考勤调休额度、SmartApp 应用额度或短信邮件额度当成这个限额。

## 额度弱提示

业务命令的 JSON `meta` 里可能出现 CLI 自己给出的额度弱提示，当前字段是 `meta.quotaHint`（同一行文案也会写到 stderr）。

- 是否提示、提示什么、什么时候不再提示全部由命令决定。本 Skill 不复述、不计算、不定义触发条件，也不要自行编造额度文案或数字。
- Agent 只需先完成当前请求，再在回复末尾把 `meta.quotaHint.message` 按原文弱提示一次；同一条提示不重复展示。
- 弱提示不是命令失败：不要因此重试业务、重新登录或重跑 `tenant quota` 重新计算。
- 弱提示和 HTTP 429 是两件事，两者都不要混进业务结果列表；429 仍按下文流程处理。

## 遇到 HTTP 429

429 **不一定是额度用完**。也可能是短时间请求过多，服务端限流。两种情况都要**立刻停止**本轮后续 i人事业务调用，不要继续打剩下的命令，也不要登录或重授权。

这条规则适用于一次用户指令触发的任意多次调用，包括分页、批量查询、多员工详情、多业务域组合和自动补查。每次调用都要解析自己的 stdout JSON，并保留成功结果；发生 429 时立即停止后续调用，不能把尚未发起的调用描述成业务失败。

正常接口结果和额度信息必须分开：

1. 先按原请求汇总已经成功返回的业务域、记录或详情。
2. 再单独输出一次额度提示，使用该次失败 envelope 的真实 `error.message`。

额度提示不能混入成功接口的结果列表，不能覆盖已经成功的业务结果，也不能只输出“第 N 次远端失败”。

然后读取 `error.message`。这是后端给用户的最终文案，必须原样引用，不得自行组织措辞：

### 1. 额度耗尽

`error.message` 含「通过智能体调用 i人事的额度已用完」。

- 已经成功的结果仍然有效，按已完成部分作答。
- 最终回答先展示已成功的业务结果，再单独输出额度提示；后续尚未发起的调用不属于业务失败结果。
- **不要**把尚未发起的调用解释成「从第 N 条开始数据错误 / 前 80 条对、后 20 条业务失败」。那些调用没有执行。
- 当前失败调用的结构化 `error.code` 和 `error.message` 要原样用于错误说明；不要用“第 N 次远端失败”或泛化的网络错误替代额度原因。
- 必须完整输出整段 `error.message`。以下写法都错误：`额度已用完：1030/1030`、`第 223 条失败：额度不足`、`因额度限制停止`。省略“本次操作未执行”“额度将在下月 1 日自动刷新”或“如需提前恢复使用，请联系 i人事服务人员申请扩容”任意内容，都属于违反本契约。
- 同一轮回复里，额度耗尽提示**只出现一次**，放在业务答案后面。用 CLI 原句，不要改写数字。
- 本月不要对同一失败自动重试。这不是「稍后重试」能恢复的暂时性限流。

典型文案：

> 当前租户本月通过智能体调用 i人事的额度已用完（x/x 次），本次操作未执行。额度将在下月 1 日自动刷新；如需提前恢复使用，请联系 i人事服务人员申请扩容。

### 2. 请求过多

同样是 HTTP 429，但没有上述额度文案。

- 同样停止后续调用。
- 不要说额度已经用完，也不要改走登录。
- 告知当前请求过于频繁，请稍后再试。
- 已成功结果照常保留。
- 请求过多的提示也要与正常接口结果分开；不要把未执行部分描述成业务失败。

当前 CLI **不会**把网关 `-429` 提升为第一层 `code`；第一层 `code` 仍只给超级密码鉴权。
