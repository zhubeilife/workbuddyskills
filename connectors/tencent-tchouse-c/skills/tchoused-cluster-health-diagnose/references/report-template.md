# 集群健康诊断报告模板

> **何时使用本文件**：在步骤 7（综合分析与生成报告）时，按此模板格式输出诊断报告。
> **何时不使用**：根因分析逻辑请参考 `diagnosis-framework.md §4`；工具调用参数请参考各工具的 reference 文档。

---

## 报告格式

> 下述五段均为**强制必填**，缺一不可。字段清单详见末尾「[五段必填字段清单](#五段必填字段清单)」。

```markdown
# 集群健康诊断报告

## 一、基线（集群概况）

- **集群 ID**：xxx
- **集群名称**：xxx
- **版本**：Doris xxx（如 doris-2.0.3）
- **状态**：Serving / Init / Changing / Isolated
- **架构**：存算一体 / 存算分离（SSC）
- **节点数**：FE x 个，BE x 个，CN x 个（如有）
- **HA 模式**：是/否（FE 三元组 `(M, F, O) = (x, y, z)`，拓扑闭环判定：✅闭环 / ❌不闭环）
- **副本数**：默认 N 副本
- **节点规格**：FE xC xG / BE xC xG / CN xC xG
- **磁盘**：类型 xxx，容量 xxx GB/节点

## 二、节点（状态矩阵）

| 节点 IP | 角色 | 子角色 (FeRole) | 状态 | CPU | 内存 | 磁盘 | 备注 |
|---------|------|--------|------|-----|------|------|------|
| 10.x.x.x | FE | MASTER | Running | 25% | 55% | — | 正常 |
| 10.x.x.x | FE | OBSERVER | Running | 18% | 50% | — | 正常 |
| 10.x.x.x | BE | — | Running | 45% | 62% | 78% | 正常 |
| 10.x.x.x | BE | — | Running | 82% | 71% | 92% | ⚠️ CPU高/磁盘高 |
| 10.x.x.x | CN | — | Running | 30% | 40% | — | 正常 |
| ... | ... | ... | ... | ... | ... | ... | ... |

## 三、事件（告警/事件列表）

（如有未处理告警事件则展示，无则必须显式写明"无待处理告警事件"）

| 时间 | 事件类型 | 描述 | 严重程度 | 状态 |
|------|---------|------|---------|------|
| 2026-xx-xx HH:mm | DiskHigh | BE 磁盘使用率超过90% | 🔴 高 | 待处理 |
| ... | ... | ... | ... | ... |

## 四、监控（指标双窗）

### 4.1 瞬时栏（1h 窗，Period=60）

| 指标 | FE/节点 | 当前值 | 阈值 | 状态 |
|------|--------|--------|------|------|
| CpuUsage | BE-10.x.x.x | 85% | > 80% 警告 | 🟡 |
| MemUsage | BE-10.x.x.x | 92% | > 85% 警告 | 🔴 |
| ... | ... | ... | ... | ... |

### 4.2 趋势栏（24h 窗，Period=300）

| 指标 | FE/节点 | 走势 | 拐点/斜率 | 备注 |
|------|--------|------|---------|------|
| DiskUsage | BE-10.x.x.x | 72% → 92% | 在 18:00 险奇4% | Compaction 堆积可能是原因 |
| DorisBeTabletCumulativeMaxCompactionScore | BE-10.x.x.x | 80 → 1200 | 连续 6h 上升 | 写入频率过高 |
| ... | ... | ... | ... | ... |

> ⚠️ 若某个维度数据缺失，在该栏明确标注「{维度} 数据不可用」；若缺失属于「核心维度（CPU/内存/磁盘/Tablet 健康度）」，评分需封顶 75。

## 五、结论

### 5.1 健康评分

🟢/🟡/🔴 **[评分等级]** — [一句话总结当前集群健康状况]

（如有「核心维度数据缺失」触发封顶，明确写明：「{维度名} 数据缺失 → 评分封顶 75」）

### 5.2 异常项详情与根因分析

#### 问题 1：[问题标题，如"BE 节点 10.x.x.x 磁盘使用率 92%"]

- **严重程度**：🔴 高 / 🟡 中 / 🟢 低
- **影响范围**：[受影响的节点/服务/业务]
- **根因分析**：[基于数据的根因判断，说明推理过程]
- **证据**：
  - [支撑结论的监控数据，如"DiskUsage 从 xx:xx 开始持续上升"]
  - [关联的告警事件，如"DiskHigh 告警于 xx:xx 触发"]
  - [其他佐证，如"DorisBeTabletCumulativeMaxCompactionScore 异常高达 xxx"]

#### 问题 2：[问题标题]

- ...

（如无异常项，补充一句「未发现异常，集群运行健康」）

### 5.3 修复建议

| 优先级 | 操作 | 预期效果 | 风险 | 建议执行时间 |
|--------|------|---------|------|-------------|
| P0 | [立即执行的操作] | [预期效果] | [风险说明] | 立即 |
| P1 | [建议执行的操作] | [预期效果] | [风险说明] | 低峰期 |
| P2 | [后续优化建议] | [预期效果] | [风险说明] | 计划内 |

### 5.4 后续建议

1. [长期优化建议1，如"建议启用动态分区自动清理过期数据"]
2. [长期优化建议2，如"建议将高频小批量写入合并为大批量（≥4096 行）"]
3. [监控建议，如"建议对 DiskUsage 设置 80% 预警阈值，对 DorisFeTabletStatusCountTypeUnhealthy 设置 >0 即告警"]
```

## 五段必填字段清单

> 本表用于报告结束后自检；任一必填字段缺失 → 报告不合格，需补齐后才能输出给用户。

| 段名 | 必填字段 |
| --- | --- |
| 一、基线 | 集群 ID、名称、版本、状态、架构、节点数、HA 模式（含三元组 `(M, F, O)` 与闭环判定）、副本数、节点规格、磁盘 |
| 二、节点 | 节点状态矩阵（含 IP / Role / FeRole / Status / CPU / 内存 / 磁盘 / 备注）；异常节点备注明确标注 |
| 三、事件 | 告警事件列表（含时间 / 类型 / 描述 / 严重程度 / 状态）；无事件需显式写明「无待处理告警事件」 |
| 四、监控 | 1h 瞬时栏 + 24h 趋势栏 两份表格；每份含指标 / 节点 / 值-走势 / 阈值-拐点 / 状态；缺失需逐项标注 |
| 五、结论 | 健康评分（🟢/🟡/🔴 + 一句话总结） + 异常项详情与根因（含证据） + 修复建议（P0/P1/P2 排序） + 后续建议 |

---

## 格式要求

1. **数据真实性**：所有诊断结论必须基于工具返回的真实数据，不得编造监控指标或告警信息
2. **证据链完整**：每个根因分析必须有对应的监控数据或事件作为证据支撑
3. **建议可执行**：修复建议必须具体到可执行的命令或操作步骤
4. **风险标注**：涉及数据变更或服务中断的操作必须标注风险和建议执行时间
5. **优先级明确**：多个问题并发时，按"防数据丢失 → 防数据可用性受损 → 恢复服务 → 性能优化"排序
6. **关联引导**：如果问题根因涉及其他 Skill 的能力范围（如慢 SQL），在报告末尾建议用户使用对应 Skill

## 特殊场景报告补充

### 场景：集群正在变更中

在报告开头增加提示：

```markdown
> ⚠️ **注意**：集群当前有操作进行中（{FlowName}，进度 {FlowProgress}%），部分诊断数据可能受影响。建议等待操作完成后重新诊断。
```

### 场景：监控数据部分缺失

在对应章节标注：

```markdown
> ⚠️ **数据缺失**：{时间段} 的监控数据不可用（可能是采集中断），以下分析基于可用时段的数据。
```

### 场景：根因无法自动定位

在根因分析部分：

```markdown
### 问题 N：[问题标题]

- **严重程度**：...
- **影响范围**：...
- **根因分析**：无法自动定位根因
- **已排查**：
  - ✅ 已排除：[原因A]（证据：...）
  - ✅ 已排除：[原因B]（证据：...）
  - ❓ 待确认：[原因C]（需要更多信息：...）
- **建议**：建议提工单并附上本诊断报告，由运维团队进一步排查
```

### 场景：副本异常提示进一步手工排查

```markdown
> 💡 **副本异常补充信息**：监控指标发现 N 个不健康副本，结合节点状态与告警事件推断主要分布在 BE [10.x.x.x, ...]。建议到 SQL 工作区执行 `SHOW REPLICA STATUS WHERE STATUS != "OK"` 与 `SHOW BACKENDS` 确认，并优先检查上述 BE 状态。
```
