## §1 性能瓶颈识别

从 Doris 执行计划（EXPLAIN / EXPLAIN VERBOSE）中识别以下问题：

| 问题类型 | 执行计划特征 | 严重程度 | 优化方向 |
|---------|------------|---------|---------|
| 全表扫描 | OlapScanNode `partitions=N/N`、`tablets=M/M`、未命中前缀索引 | 🔴 高 | 添加分区过滤 / 调整 KEY 列顺序 |
| 索引缺失 | 等值/范围过滤未命中前缀索引、ZoneMap 或 BLOOM_FILTER | 🔴 高 | 添加 BLOOM_FILTER / INVERTED INDEX / 调整 KEY |
| 分区裁剪失败 | `partitions=N/N`（N=总分区数），未命中分区键 | 🔴 高 | 添加分区键过滤条件 |
| Shuffle Join 代价高 | HashJoin 节点 distributionMode=SHUFFLE，但表本可 Colocate | 🟡 中 | 调整为 Colocate Join 或 Broadcast |
| Broadcast 大表 | 右表行数大却被 BROADCAST | 🟡 中 | 改为 Shuffle 或调整 JOIN 顺序 |
| 数据倾斜 | 某些 Tablet 数据量远大于其他、`scanRows` 在 BE 间分布不均 | 🟡 中 | 调整分桶键 / 增加 BUCKETS |
| RF 未生效 | RuntimeFilter 未推到 ScanNode | 🟡 中 | 调整 session 变量 / 改写 SQL |
| 排序开销大 | TopN 节点处理大量数据 | 🟡 中 | 利用 Key 列前缀排序 / 加索引 |
| SELECT * 宽表 | 读取大量不必要的列 | 🟡 中 | 只选需要的列 |
| 子查询重复执行 | 标量子查询未被改写为 JOIN | 🟡 中 | 改写为 JOIN |
| Compaction 落后 | 单 Tablet rowset 数过多导致 ScanNode 慢 | 🟡 中 | 提升 Compaction 并发 / 合并写入批量 |

### 判定优先级

当一条 SQL 存在多个问题时，按以下优先级排序处理：

1. 分区裁剪失败（影响最大，通常是数量级的差异）
2. 全表扫描 / 索引缺失
3. JOIN 算法不优（Shuffle/Broadcast 错配）
4. 其他问题

## §2 执行计划关键字段解读

### OlapScanNode（最重要）

```
OlapScanNode
  TABLE: db.tbl
  PREAGGREGATION: ON  -- 是否开启预聚合（AGGREGATE 模型重要）
  PREDICATES: dt >= '2026-06-09'
  partitions=3/30      -- 命中分区数 / 总分区数
  tablets=24/240       -- 命中 tablet 数 / 总 tablet 数
  cardinality=10000000 -- 估算行数
  avgRowSize=200
```

**关键判断**：
- `partitions=A/B`：A ≈ B → 分区裁剪未生效（全分区扫描）
- `tablets=A/B`：A ≈ B → 分桶裁剪也未生效，全 Tablet 扫描
- `PREAGGREGATION: OFF` 且为 AGGREGATE 模型 → 预聚合失效（如 SELECT 了非 KEY 非聚合列）

### HashJoin 节点

```
HASH JOIN
  join op: INNER JOIN(BROADCAST/PARTITIONED/COLOCATE)
  hash predicates: a.id = b.id
  runtime filters: RF000[bloom_filter] <- b.id
```

**关键判断**：
- `BROADCAST`：右表会广播到每个 BE，右表过大可能导致 OOM
- `PARTITIONED`（即 Shuffle Join）：双方都按 hash 重分布，IO 开销大
- `COLOCATE`：双方相同 Colocate Group 且分桶相同，无 shuffle，最优
- `BUCKET_SHUFFLE`：左表是分桶键时，仅右表 shuffle

### AGGREGATE 节点

```
AGGREGATE (merge finalize)
  output: sum(a.amount)
  group by: a.dt, a.channel
```

**关键判断**：
- group by 列基数过高（如用户 ID）→ 聚合开销大，考虑物化视图加速

### EXCHANGE 节点

```
EXCHANGE NODE
  type: HASH_PARTITIONED / UNPARTITIONED / BROADCAST
```

**关键判断**：
- 频繁出现 BROADCAST 大表 → JOIN 顺序需调整
- 多次 HASH_PARTITIONED → 数据 shuffle 多，可考虑分桶/Colocate

## §3 输出报告格式

### 优先级标注规范（强制）

本报告中所有优化建议**必须**使用 `P0`/`P1`/`P2` 三级优先级，不允许使用 `⭐⭐⭐`、`高/中/低`、`重要/次要` 等其他写法。

| 优先级 | 定义 | 处理时限 |
| --- | --- | --- |
| `P0` | 直接影响业务（OOM / 查询失败 / 阻塞 / 磁盘即将打满） | 立即处理 |
| `P1` | 明显的性能瓶颈（全表扫描 / JOIN 不优 / Compaction 落后） | 本周内处理 |
| `P2` | 可观察性/工程化优化（统计信息过期 / Hint 微调 / 索引预热） | 可排期处理 |

**每条建议必须包含的字段**：

- `预期收益`：量化描述优化后的改善幅度，例如「扫描行数从 1.2 亿 → 300 万，耗时从 8s → 预计 800ms」。不能量化时至少说明定性改善（「避免 OOM」「消除全分区扫描」）。
- `实施成本`：从三个维度说明——1) 是否需重建表/补数；2) 是否要求业务代码改动；3) 是否需要运维窗口 / 重启。例如「仅需 ALTER TABLE 动态生效，无需重建」「需 BUILD INDEX，耗时约 30 分钟，建议低峰期执行」。

### 报告模板选择

根据步骤 3.5 的去重结果，选择对应的报告模板：

- **标准模板**：去重后有 ≥ 2 个不同 SQL 模式 → 使用下方标准格式
- **高频单一 SQL 模板**：去重后仅 1 个模式（或某模式占比 > 90%）→ 使用 [高频单一 SQL 变体](#高频单一-sql-报告变体)
- **小样本模板**：本次全量样本数 < 5 条 → 使用 [小样本变体](#小样本报告变体)


### 高频单一 SQL 报告变体

当去重后仅 1 个 SQL 模式（或某模式占比 > 90%）时，使用以下报告结构替代标准的"逐条诊断"部分：

```markdown
## 高频慢 SQL 深度分析

### 基本信息
- **SQL 模式**：（归一化后的 SQL 文本）
- **执行频次**：共 xxx 次（时间范围内）
- **执行频率**：约每 X 分钟/小时执行一次
- **最大耗时**：xxx ms
- **平均耗时**：xxx ms
- **累计资源消耗**：平均耗时 × 频次 = xxx 秒（总计浪费）

### 执行频次分析
- 时间分布：（是否集中在某个时段？如每天凌晨 2:00-3:00）
- 频率模式：固定间隔 / 随机触发 / 业务高峰集中
- 持续天数：从 xxx 开始，持续 N 天

### 高频原因推测
| 可能原因 | 判断依据 | 可能性 |
|---------|---------|--------|
| 定时任务/Cron Job | 固定间隔执行 | 高/中/低 |
| 应用层轮询 | 高频随机触发 | 高/中/低 |
| 缓存失效后回源 | 突发集中执行 | 高/中/低 |
| ETL/数据同步任务 | 凌晨集中执行 | 高/中/低 |

### 性能瓶颈（同标准模板）
- **诊断依据**：🟢/🟡/🔴
- **瓶颈详情**：...

### 优化建议

#### SQL 层优化
- [SQL 改写方案]

#### 应用层优化（针对高频特征）
- **缓存策略**：对结果集添加 TTL 缓存，降低查询频次
- **增量同步**：如为全量同步任务，改为增量方式
- **降频建议**：将执行间隔从 X 分钟调整为 Y 分钟
- **物化视图**：对固定聚合查询创建异步/同步物化视图，将查询耗时降至毫秒级

#### 预期收益
- SQL 优化收益：单次耗时从 xxx ms 降至 xxx ms
- 频次优化收益：若降频 50%，累计节省 xxx 秒/天
- 综合收益：xxx
```
