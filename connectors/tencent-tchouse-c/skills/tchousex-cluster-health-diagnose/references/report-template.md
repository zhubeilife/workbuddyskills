# 集群健康诊断报告模板（TCHouseX / Impala）

> **何时使用本文件**：在步骤 7（综合分析与生成报告）时，按此模板格式输出诊断报告。
> **何时不使用**：根因分析逻辑请参考 `diagnosis-framework.md §4`；工具调用参数请参考 `./api-reference.md`。

---

## 报告格式

```markdown
# 集群健康诊断报告

## 实例概况

- **实例 ID**：instance-xxx
- **实例名称**：xxx
- **版本**：Impala xxx（如 1.8.0）
- **状态**：运行中(0) / 异常(1) / 创建中(2) / 变配中 / 已过期(5)
- **节点拓扑**：Master(FE) x 个、Core(Executor) x 个
- **计算组（Warehouse）**：x 个
- **节点规格**：xC xG（CPU/内存）
- **磁盘**：类型 xxx，容量 xxx GB/节点

## 健康评分

🟢/🟡/🔴 **[等级] XX / 100 分** — [一句话总结当前实例健康状况]

### 扣分明细

（若未扣分则标注"无扣分项"；数据不充分时仅给定性等级，不填分数）

| 扣分项 | 具体现象 | 扣分 | 依据（见 diagnosis-framework.md §3） |
|--------|---------|------|-------------------------------------------|
| 实例/节点异常 | 例：Warehouse `default` 有 1 个 CN 节点非运行 | -8 | 扣分项 A |
| 操作记录 | 例：24 小时内 1 条失败状态的升配操作 | -15 | 扣分项 B |
| 资源使用量 | 例：Storage 使用率 88%（严重阈值） | -15 | 扣分项 C（Storage 使用率） |
| SQL 运行 | 例：失败 SQL 占比 25%（严重阈值） | -15 | 扣分项 D（失败占比） |
| SQL 运行 | 例：慢 SQL 占比 12%（警告阈值） | -4 | 扣分项 D（慢 SQL 占比） |
| ... | ... | ... | ... |
| **合计** | | **-XX** | 最终得分 = 100 - XX = **YY** |

> 若因"强制降级规则"导致等级与分数不一致（如得分 92 但存在 Master 节点异常），在此标注降级原因。

## 节点/计算组状态矩阵

### Master(FE) & Core(Executor) 节点

| 角色 | 节点数 | 规格 | 状态 | 备注 |
|------|--------|------|------|------|
| Master(FE) | 3 | 8C32G | 运行中 | 正常 |
| Core(Executor) | 4 | 16C64G | 运行中 | 正常 |

### 计算组（Warehouse）

| 计算组 | CN 数 | 规格 | 状态 | 实时 CPU | 备注 |
|--------|-------|------|------|---------|------|
| default | 4 | 16C64G | 运行中 | 45% | 主计算组，正常 |
| etl | 2 | 32C128G | 运行中 | 82% | ⚠️ ETL 计算组 CPU 高 |
| ad-hoc | 2 | 16C64G | 变更中(50%) | — | ⚠️ 变更中，暂无法诊断 |

## 资源使用量摘要

| 资源类型 | 当前使用量 | 使用率 | 时间窗 & 粒度 | 趋势 | 数据可用性 | 备注 |
|---------|-----------|--------|--------------|------|-----------|------|
| Storage（存储） | xxx GB | xx% | 近 7 天 / Day | 增速 +xx%/日 | 可用 / 部分可用 / 不可用（RequestId=xxx） | 🟢/🟡/🔴 |
| Warehouse（计算 CPU 时序均值） | xx% | — | 近 24 小时 / Hour | 平稳/上升/波动 | 可用 / 不可用（RequestId=xxx） | 🟢/🟡/🔴 |

> 💡 当 Storage 数据可用性为"不可用"时，说明命中已知后端 InternalError（详见 SKILL.md 步骤 3），此时扣分项 C 的 Storage 部分不计入评分；若已通过 `VirtualClusters` 拿到当前磁盘水位快照，可标为"部分可用"并在备注中说明"仅当前时刻快照，无趋势"。

## 最近集群操作记录

（如果 24 小时内有变更操作则展示，无则标注"无最近操作"）

| 操作时间 | 操作对象 | 操作名称 | 执行人 | 状态 |
|----------|---------|----------|--------|------|
| 2026-xx-xx HH:mm | Warehouse default | 升配 | 100xxxx | ✅ 成功 |
| 2026-xx-xx HH:mm | Instance | 重启 Coordinator | 100xxxx | 🔴 失败 |

## SQL 运行情况摘要

| 指标 | 数值 | 状态 |
|------|------|------|
| 近 1 小时失败 SQL 占比 | x% | 🟢/🟡/🔴 |
| 近 1 小时慢 SQL（> 60s）占比 | x% | 🟢/🟡/🔴 |
| 单条最长运行时长 | xxx s | 🟢/🟡/🔴 |
| 同一异常 SQL 重复次数 TopN | Statement 前 40 字符 x N 次 | 🟢/🟡/🔴 |
| 异常 QueryID 样本（最多 3 条用于深入分析） | 列出 QueryID + 错误类型 | — |

## 异常项详情与根因分析

### 问题 1：[问题标题，如"近 1 小时失败 SQL 占比 25%，共 120 条异常"]

- **严重程度**：🔴 高 / 🟡 中 / 🟢 低
- **影响范围**：[受影响的计算组/用户/SQL]
- **根因分析**：[基于数据的根因判断，说明推理过程]
- **证据**：
  - [支撑结论的 SQL 历史记录或资源用量时序]
  - [QueryID + Profile 关键耗时算子，如有]
  - [其他佐证，如"操作记录显示 xx:xx 有 Warehouse 升配操作，可能是诱因"]

### 问题 2：[问题标题]

（如无异常项，标注"未发现异常，实例运行健康"）

## 修复建议

> ⚠️ **所有 SQL 命令类修复（如 `KILL QUERY` / `INVALIDATE METADATA` / `DROP PARTITION` / `COMPUTE STATS` 等）均为建议，需由用户在自己的 SQL 客户端或控制台 SQL 工作区手动执行；本 Skill 不代执行**。

| 优先级 | 操作 | 预期效果 | 风险 | 建议执行时间 |
|--------|------|---------|------|-------------|
| P0 | `KILL QUERY <query_id>` 终止异常长查询 | 立即释放资源 | 业务方查询中断 | 立即 |
| P0 | `ALTER TABLE xxx DROP PARTITION 'yyyymm'` 清理过期分区 | 释放存储空间 | 数据不可恢复，需确认过期 | 立即 |
| P1 | `INVALIDATE METADATA <db>.<tbl>` 刷新元数据 | 消除元数据延迟 | 首次查询延迟增加 | 低峰期 |
| P1 | 按业务拆分 Warehouse | 在线/批量隔离，消除干扰 | 需控制台操作 | 计划内 |
| P1 | 优化慢 SQL（改写 / 加过滤 / 更新统计）| 根本降低 CPU/内存消耗 | 需 SQL 改写 | 低峰期 |
| P2 | `COMPUTE STATS <db>.<tbl>` 更新表统计 | 优化 JOIN 顺序 | 消耗资源 | 低峰期 |
| P2 | 扩容 Core(Executor) 节点或加大磁盘 | 根本解决容量不足 | 需控制台操作 | 计划内 |

> ⚠️ 涉及计算组重启、配置变更、扩缩容等控制台操作，建议在低峰期执行。

## 后续建议

1. [长期优化建议1，如"定期 COMPUTE STATS 维护表统计信息（数据量变化 > 10% 时）"]
2. [长期优化建议2，如"高频小批量写入合并为大批量（≥ 256MB/文件）"]
3. [监控建议，如"对 Storage 使用率设置 70% 预警阈值，对失败 SQL 占比设置 5% 预警"]
4. [架构建议，如"在线分析与批量 ETL 拆分 Warehouse 隔离"]
```

## 格式要求

1. **数据真实性**：所有诊断结论必须基于工具返回的真实数据，不得编造监控指标、资源用量或告警信息
2. **证据链完整**：每个根因分析必须有对应的 SQL 历史记录 / Profile 关键算子 / 资源用量时序 / 操作记录作为证据
3. **建议可执行**：修复建议必须具体到可执行的命令（如 `KILL QUERY`、`INVALIDATE METADATA`、`COMPUTE STATS`、`DROP PARTITION`）
4. **风险标注**：涉及数据变更或服务中断的操作必须标注风险和建议执行时间
5. **优先级明确**：多个问题并发时，按"防数据丢失 → 恢复服务 → 性能优化"排序
6. **关联引导**：如果根因涉及慢 SQL，本 Skill 只输出 Profile 关键算子与初步建议；进一步的 SQL 改写、执行计划优化等深度调优不在本 Skill 范围内，告知用户可由后续专门的慢 SQL 诊断能力承接
7. **评分可追溯**：健康评分必须附扣分明细表，总分 = 100 减去各项扣分；扣分规则遵循 `diagnosis-framework.md §3`，不得自行发挥分数
8. **SR 接口不出现**：报告中不得出现任何 SR（StarRocks）相关的接口名或指标（本 Skill 明确排除）

## 特殊场景报告补充

### 场景：实例正在变更中

在报告开头增加提示：

```markdown
> ⚠️ **注意**：实例当前有操作进行中（{FlowName}，进度 {FlowProgress}%），部分诊断数据可能受影响。建议等待操作完成后重新诊断。
```

### 场景：某个 Warehouse 正在变更中

在计算组表格中标注：

```markdown
> ⚠️ **注意**：计算组 `{VirtualCluster}` 正在变更中（{FlowName}，进度 {FlowProgress}%），该计算组的诊断数据可能不准确。
```

### 场景：SQL 历史不可用

```markdown
> ⚠️ **数据缺失**：`DescribeSqlHistoryRecords` 调用失败，无法获取近期 SQL 运行情况。本报告仅基于 `DescribeInstance` / `DescribeInstanceWarehouse` / `DescribeInstanceResourceUsage` / `DescribeInstanceOperationsV1` 给出有限分析，扣分项 D 未计入。
```

### 场景：资源使用量数据不可用

```markdown
> ⚠️ **数据缺失**：`DescribeInstanceResourceUsage` 调用失败，Storage/Warehouse 用量趋势不可用，扣分项 C 未计入，评分可能偏乐观。
```

### 场景：Storage 时序不可用（后端已知 InternalError）

```markdown
> ⚠️ **Storage 时序数据不可用**：命中已知后端问题（`ResourceType=Storage` 返回 `InternalError`，RequestId=`xxx`）。已按 SKILL.md 步骤 3 降级为 `Period=Day` 重试，仍失败。本报告中 Storage 趋势基于 `VirtualClusters` 当前磁盘水位快照（若可用），**扣分项 C 的 Storage 部分不计入**；建议附本 RequestId 向云 API 团队提交工单排查。
```

### 场景：根因无法自动定位

```markdown
### 问题 N：[问题标题]

- **严重程度**：...
- **影响范围**：...
- **根因分析**：无法自动定位根因
- **已排查**：
  - ✅ 已排除：[原因A]（证据：...）
  - ✅ 已排除：[原因B]（证据：...）
  - ❓ 待确认：[原因C]（需要更多信息：...）
- **建议**：建议提工单并附上本诊断报告（含 RequestId 和关键 QueryID），由运维团队进一步排查
```
