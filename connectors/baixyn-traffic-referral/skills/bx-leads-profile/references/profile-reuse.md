# 公司资料供其他宿主能力复用

这是一份上下文组织约定，不是新的 MCP 工具或 API 请求体。业务工具参数以 tools.md 和当前会话 Schema 为准。

## 先确定用哪份资料

| 来源 | 可声称的状态 | 处理 |
| --- | --- | --- |
| profile_get，或 profile_draft_save 成功回执中的 profile | 已保存 | 默认输入；保留 version/updatedAt 供后续核对 |
| profile_draft_get 的 data.data / profile_draft_preview 的 data.data | 尚未保存草稿 | 用户明确要求使用这份草稿时才能用于创作，标清状态 |
| company_analysis_get 的已完成报告 | 解析建议，未采用 | 展示供确认；用户明确要求仅用建议起稿可做，不称已确认事实 |

无正式资料时不要用对话里另一家公司的报告冒充 profile_get。读取失败与空资料分别说明；授权错误先按宿主流程重连，不使用旧账号缓存继续工作。

## 给下游的背景结构

用用户可读的结构化文字或 JSON，包含下列有实际依据的内容，不附整份原始 MCP 响应：

- 状态、公司名称、官网、读取时间；保留资料版本作溯源，不塞进最终营销文案。
- 公司介绍 overview；全部 productItems 逐条 name + description；industryItems 与 businessAreas 同样逐条；公司身份 roles。
- 长期目标市场 markets；空数组代表全球/不限国家，不是解析失败。
- 每项来源状态：manual 为用户填写，edited 为用户编辑，ai 为解析采用；evidence.basis 区分 explicit 与 inferred。没有来源信息时标“未提供来源”，不能称经官网验证。
- 对当前用途确实影响内容的缺项，如认证、规格、品牌语气或目标受众；有缺项可先写条件化草稿，不自行补成事实。

官网没有统一 websiteOrigin 字段；只按 websiteEvidence（若有）说明来源。正式资料里附带的 analysis 可能仅是最近一份报告，不用它覆盖当前各条目。updatedAt 正式资料可为毫秒时间戳，草稿可为 ISO；未返回则不编造更新时间。

## 按用途传递，不扩大行动范围

| 用户请求 | 可提供的输入 | 尚需该能力处理的部分 |
| --- | --- | --- |
| 为公司做网站/落地页 | 公司介绍、全产品、场景、已保存官网、市场 | 宿主实际建站工具、版式/素材；发布依用户指令，读取资料不等于公开发布 |
| 写社媒内容 | 产品、用途、品牌/来源、目标市场 | 宿主写作与平台形式；没有账号/发布工具就只交付文案 |
| 写开发邮件 | 公司能力、指定产品、目标买家、用户已提供的目标或已有交付公司的理由（按已知任务ID读取） | 不把推测采购关系写成已确认需求；不生成收件人地址，不自动发送 |
| 准备投流内容 | 真实产品、用途、市场、已确认卖点与落地页信息 | 宿主实际投流能力；不自动建广告、开启预算或投放 |
| 继续找客户 | 最新正式资料及所有产品 | 由买方路线 Skill 调用现有后台，不能把未保存草稿当正式搜索快照 |

上述资料是按需复用的业务背景，不要求邮件、社媒、建站、投流都先解析、选路线或付费找客。已有资料和授权直接复用；只补影响当前任务的缺项，完成后回到原任务。

只有用户提出触达、发布或第三方上传等动作，且宿主确实具备相应工具和权限，才按它们的规则继续。这里不制造 cross-skill 工具名、不代传Token、不自动调用 sales_inquiry_submit；该工具仅用于用户明确要求登记企业服务咨询。

## 典型边界

- “看看资料，帮我写主页”只读即可；不创建解析、草稿、找客任务或奖励领取动作。
- “解析这个官网”先展示报告；不能因为下游想建站就默认为全部采用并保存。
- “全部采用并保存，再写主页”逐项采用后统一保存；成功后从保存回执组织背景。若同字段冲突，先解决冲突，不能用未保存内容声称正式资料。
- MCP只改国家、网页同时改产品：交给服务端按字段合并，保留网页最新产品。双方改同一条说明：展示差异由用户选择，禁止换基线绕过冲突。
- 草稿多了无关修改：不为完成下游任务顺带保存；读取正式资料创作，或按用户确认的草稿范围处理。
- 换账号/换公司：重新读取并重新绑定；同一名称不证明同一主体。
