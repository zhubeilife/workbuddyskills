# 容错与续跑规范（长任务生死线）

> 本文固化「长任务不分块 + 无检查点一次性大产出」导致残卷的根因，以及「失败只补坏题、成功永不丢失」的四层防护与断点续跑协议。
> 适用于链路 A（标准组卷）与链路 B（题找题）的一切"多题 × 多次 API"长任务。

---

## 1. 典型问题与根因（为什么"25 题只落 6 题"）

**现象**：25 题组卷运行 >1 小时，只落盘 no.20–25（6 题），1–19 全缺。

**根因（有 transcript 证据）**：
1. **不是 API 失败** —— 25 次搜索 + 25 次解析**全部成功返回**（仅 2 次 429，已重试）。
2. 把 50 条大结果（每条搜索 20–30KB HTML，累计 **≈0.97 MB**）塞进**单个子代理**上下文。
3. 上下文逼近窗口上限 → 系统**自动压缩**（插入 `<conversation_history_summary>`）。
4. 压缩摘要**失真**（把"1-10 选择 / 11-20 多选 / 21-25 解答"写成"1-21 / 22-25"）且**丢弃 1-19 的槽位定义与已抓数据**。
5. 子代理只剩"最近处理的 6 题"→ 写盘只落 6 题，并自述"1-19 无法重建"。
6. 主线程误判为"取数失败" → **整包重发** → 套娃。

**一句话**：**「无检查点的一次性大产出」在长任务里必然失败**；失败后**没有续跑逻辑** → 只能整体重来。

---

## 2. 四层防护（强制）

### A. 预防（让失败不发生）
| 措施 | 口径 |
|---|---|
| **分块** | 25 题切 **3 块**（①1–9 ②10–18 ③19–25），每块 ≤8–9 题 → 单块上下文 ≈1/3，远离压缩阈值 |
| **块载体按 payload 选** | **优先主线程直发并同轮并发**（子代理有启动开销：各自读 SKILL / 重读依赖 / 独立轮次）；确需隔离大 payload（长材料 / 带图解答题 / 题量大）时才用子代理，且**总数 ≤2** |
| **逐题原子落盘** | 每完成 1 题（search 选中 + analysis 到手）**立即**追加写入本块 picks 文件；**绝不**"整块跑完再写" |
| **重活不进上下文** | 搜索原始 HTML 由脚本/子代理**落盘**，模型只做"选择/引用"，不搬运 25×25KB |
| **块内上限** | 每块 ≤8–9 题；块内上下文设阈值 |

### B. 检测（尽快发现失败）
| 措施 | 脚本/口径 |
|---|---|
| **题号连续性 + 完整性校验** | `validate_picks.py --spec spec.json picks_*.json`（校验 no/kind/score/stem、analyse|method、kind/score 合 spec） |
| **识别 PARTIAL 残卷** | 文件 `status != COMPLETE` 或 `missing_slots` 非空 → **当"未完成"**触发续跑 |
| **进度心跳** | 每代理每 3 题打印 `已完成 x/N` |

### C. 恢复（幂等续跑，只补缺口）
| 措施 | 脚本/口径 |
|---|---|
| **合并 + 缺口** | `merge_and_gap.py --spec spec.json [--existing merged.json] --out merged.json picks_*.json` |
| **只补 missing** | 仅对缺失题号发新请求；**绝不重拉/覆盖已成功的好题** |
| **有界重试** | 单题重试 ≤2 次，仍失败 → 记入 missing 并**继续**（不阻断整卷）。⚠️ **仅限「零星 / 参数级」失败**；**服务级**接口错误**连续 2 次 → 见 §6，立即中止并返回错误** |
| **逐级降级** | `放宽 dg → 去 so → 关键词兜底（mcp__<SERVER>__tkSearchQuestion）` |

### D. 兜底（最后保障）
| 措施 | 口径 |
|---|---|
| **主线程接手** | 子代理不可靠时，主线程按 `missing` 直接补拉 |
| **降级交付** | 仍缺题 → 交"**N/M 题成品 + 缺题清单**"，**绝不 0 交付** |
| **检查点保留** | 分块 picks 文件**永久保留**为断点，不被后续步骤删除 |

## 3. 断点续跑协议

```
阶段A  3 块并行拉取（逐题原子落盘 + 每3题报进度）
阶段B  validate_picks() 校验 → merge_and_gap() 算 missing
阶段C  missing 非空 ? 只补 missing（幂等，≤4 并发，有界重试）→ 回阶段B
       : 进阶段D
阶段D  收尾用**一条命令**：finish.sh（= 校验 → 幂等合并 → 组装 → 渲染导出 → 自检，**1 轮**）
       → 退出码 2/3 ? 降级交付（缺题清单）: 正常交付
```

**关键不变量**：
- 任意时刻，**已落盘的好题永不被更差的覆盖**（`merge_and_gap` 取"更完整者"）。
- 任意失败点，**只需重做 missing 题号**，成本 ∝ 缺口数，与已成功数无关。

## 4. 分块重叠转档（与拉题并行，可选快路径）

「拉题」是网络 I/O，「转 docx（图嵌入）」是本地 CPU，二者**无数据依赖** → 可重叠：

```
块①拉完 → render_blocks 立刻转块①docx  ┐
块②拉完 → render_blocks 立刻转块②docx  ├ 与仍在拉取的块重叠
块③拉完 → render_blocks 立刻转块③docx  ┘
→ merge_docx 把 3 份缝合为「试卷 docx / 解析 docx」+ render_blueprint 出细目表
```

- 脚本：`build_questions.py --split-blocks "1-9,10-18,19-25"` → `render_blocks.sh`（内部 `merge_docx.sh` 缝合）。
- 缝合用 **`docxcompose`**（正确处理**题图关系 rels**、样式、分节）；纯 XML 拼接会**丢图**。
- 分块 `questions_blockN.json` 带全局题号 + `omit_header`（非首块不重复标题/卷头），缝合后编号连续、标题不重复。

## 5. 已知坑（务必回避）

1. **多 `point[]` 合并搜题**：返回**混合列表且 `Points` 为空**，无法归属 → **默认不合并**（见 efficiency.md #2）。
2. **取消节流**：删掉 `1.5s` 间隔改纯并发 → 更易 429，**是回归**；应用「**自适应节流 + 自适应并发**」（默认 **4**；**仅题量 >20** 才探 **6**；429 回落 3）。
3. **把原始大 HTML 留在对话里**：搜题/解析返回不落盘、还让模型复述一遍写文件 → 上下文暴涨 + 二次浪费；应走「**取数与决策分离**」（`shrink_candidates.py table` 出紧凑表 → 决策只回「题位→短ID」 → `assemble` 自动回填）。
4. **分块渲染空卷**：`render_paper` 按 `sections` 的 kind 过滤；若某题型**首题不在本块**，必须仍把该 kind 列入 `sections`（title 置空即可），否则**整块丢失该题型**。（已修：`build_questions._sections_for_range` 保留 kind、空标题；`render_paper` 跳过空标题。）
5. **手工 XML 缝合 docx**：会丢图片 rels → 必须用 `docxcompose`。
6. **用「每步压缩上下文」续命**：自动压缩会**丢已读内容与已抓数据**（正是 §1 的根因）→ **禁止**；跨阶段一律**从落盘文件恢复**（`raw_*.json` / `picks_*.json` / `work-dir/`），不依赖会话记忆。
7. **把共享可写状态的步骤并行化**：`assemble`（单一 picks）/ `merge_and_gap`（单一 merged）/ `finish.sh`（单一 work-dir）/ `tkpoint_cache save`（单一缓存文件）**必须串行、各只跑一次**；只有「读同一份只读输入、各写各自输出」的子任务才可并行（详见 SKILL.md「并行边界」）。

## 6. 接口错误处置：出错立即重试一次、仍失败才停（fail-fast）

> **背景**：抓知识点树 `mcp__<SERVER>__tkPoint` 命中 **429 限流**时，若**未重试、直接改路径**（改用已知考点名硬跑），会掩盖服务级故障并使"知识点归一化"形同虚设。
> 新规：**服务级接口错误连续 2 次失败 → 立即停止任务并返回错误**，不再"悄悄换条路硬跑"。
> 新规：**服务级接口错误连续 2 次失败 → 立即停止任务并返回错误**，不再"悄悄换条路硬跑"。

> ### ⛔ 硬规则（一句话，强制）
> **任一接口调用出错（服务级）→ 立即退避重试第二次**；**若第二次仍没调通 → 立即停止当前任务、向用户返回结构化错误**，不得自动继续、不得改路径硬跑。
> 即：**出错先补一次；补不通才停。**（参数级错误 `code:500` 不触发本规则，走降级，见 §6.1。）

### 6.1 先分类，再处置（强制）

| 错误类别 | 典型表现 | 处置 |
|---|---|---|
| **服务级**（服务挂了 / 被限流 / 网络） | `429 频率限制`、请求超时、连接失败、HTTP `5xx`、接口回「系统繁忙」 | **退避重试 1 次**（`sleep 3`）→ **连续 2 次失败即中止整卷任务并返回错误**；**严禁**改路径 / 降级硬跑 |
| **参数级**（请求内容不合法） | 考点名无效 → `code:500 查询失败！` / `String index out of range: -1` | **不算服务故障、不计入连续失败计数** → 按既有规则**降级**（改关键词 `mcp__<SERVER>__tkSearchQuestion`）；内容问题不阻断整卷 |

> **一句话判据**：**「同一个接口连着坏两次」→ 停；「不同题偶发坏一次」→ 补。**

### 6.2 连续失败计数口径

- 计数键 = **接口名**（同一接口的连续调用）。
- 某次调用失败 → 计数 +1；**下一次同类调用成功 → 计数清零**。
- **计数达到 2**（＝首败 + 退避重试 1 次仍败）→ **立即中止**。**不再尝试第 3 次、不再改路径**。

### 6.3 中止时返回什么（结构化，缺一不可）

1. **接口**：失败的是哪个接口（如 `mcp__<SERVER>__tkPoint` / `mcp__<SERVER>__tkSearchSubjectQuestion`）。
2. **连续失败**：`2` 次（含首败 + 1 次退避重试）。
3. **原始错误**：最后一次的**原始错误消息**（如 `429 您的使用量已超出频率限制，将在 <时间> 重置`）。
4. **已完成题位**：已成功落盘到哪一步（哪些 `picks_*` / `raw_*` 已就绪）。
5. **建议**：恢复方式（等待限流重置 / 检查连接后**从检查点续跑**）。

> **检查点必须保留**：中止**不删**工作目录（`raw_*.json` / `picks_*.json` / `spec.json`），修复后按 §3 断点续跑协议**只补缺口**。

### 6.4 与「零星单题失败」的关系（不要过度中止）

- 本规只针对**同一接口连续 2 次**（＝服务级信号）→ **fail-fast**。
- **零星**的、非连续的单题失败（偶发一次后下一题即成功）仍走 §2C：**有界重试 ≤2 → 记 `missing` → 继续**，**不**中止整卷。
- 即：**fail-fast 管"服务级连坏"，§2C 管"内容级偶坏"，二者并存不冲突。**

### 6.5 唯一例外：链路 B 的「先降级、降级后仍败才中止」

> **默认**：服务级接口错误连续 2 次 → 中止。
> **例外**：仅当该降级是**预先文档化、且产物等价**的**既定备选**（目前仅一处：链路 B `mcp__<SERVER>__tkQuestionSame` 故障 → `mcp__<SERVER>__tkSearchQuestion` 题眼关键词召回，见 `similar-question.md §S3g`）。

**链路 B 例外路径的处置顺序（强制，不可颠倒）**：

| 步 | 动作 | 结果 |
|---|---|---|
| 1 | 首选 `mcp__<SERVER>__tkQuestionSame` 命中失败（「系统繁忙」等服务级错误） | 退避重试 1 次；仍败 → **进入降级，不算「中止」** |
| 2 | **执行预定降级**：`mcp__<SERVER>__tkSearchQuestion` 题眼关键词召回（产物等价） | 降级成功 → 继续；**必须在输出显式标注「`mcp__<SERVER>__tkQuestionSame` 连续失败，已降级为关键词召回」**，不得静默 |
| 3 | **降级路径自身也连续 2 次失败**（服务级） | → **此时才中止整卷任务并返回错误**（按 §6.3 结构化返回） |

- **判据**：**先降级、后判死**——降级是例外内的**第一步**，不是"是否可以绕过"；降级后**仍坏**才落回默认的 fail-fast。
- **计数分开**：`mcp__<SERVER>__tkQuestionSame` 的失败计数与 `mcp__<SERVER>__tkSearchQuestion` 的失败计数**各自独立**；降级切到 `mcp__<SERVER>__tkSearchQuestion` 后，**从 0 重新计数**，连续 2 次失败才中止。
- ⚠️ 反面教材：本次事故中"`mcp__<SERVER>__tkPoint` 429 → 改用已知考点名硬跑"**既非预设备选、又使归一化步骤形同虚设** → 属**违规静默改道**（且 `mcp__<SERVER>__tkPoint` **不在**本例外清单内），正被本规禁止。
