# 典型使用场景

以下示例用于说明工具选择和关键决策边界。实际调用时始终以工具实时 `inputSchema` 为准，保留查询结果返回的标准 ID，并遵守本技能的确认、错误、重试和幂等规则。分析、拟定内容和筛选对象均不代表用户已经授权发送。

## 0. 引导空间完成首次配置

示例请求：“我如何通过 3Chat 进行客户运营？”

当前空间状态未知时，先检查启动里程碑，不先查询客户。若两个里程碑都未完成，回答必须包含能力与启动原因、三步快速启动和持续优化建议；不能只给出一般运营方法或两个配置链接。

1. 当前连接空间的启动里程碑状态未知时，调用 `get_3chat_workspace_readiness`。
2. 返回 `READY` 时，不展示启动引导，继续执行用户要求的客户运营流程。
3. 两个里程碑都未完成时，按 `startup-readiness.md` 展示完整启动引导。
4. 只有一个里程碑未完成时，只展示对应的缺失步骤和返回地址。
5. 展示 `ACTION_REQUIRED` 后，用户在后续回合再次提出依赖 3Chat 的请求时，将其视为从外部配置流程返回的继续操作点，即使用户没有明确说已经完成，也要重新检查。
6. 新结果显示部分进展时，只展示仍然缺失的步骤；变为 `READY` 时，简短说明初始配置已经完成，然后继续当前请求。
7. 缺失状态没有变化时，不重复完整产品介绍，只做简短提醒，并在可能的情况下继续原始请求。
8. 用户明确表示暂不配置时，停止主动刷新，直到用户报告进展或要求重新检查。

组件呈现验收：两个里程碑都缺失时，应按“步骤 1 文字 → 3Chat 搭建助手 组件 → 步骤 2 文字 → 渠道组件 → 步骤 3 文字”展示；只缺渠道时，只展示一个文字步骤和渠道组件。宿主没有组件工具、渲染失败或无法交替排版时，在对应文字步骤下展示命名的 Markdown 链接。组件不能替代步骤文字；体验接待不使用编造的收件箱链接。

## 1. 销售跟进前查询并总结客户

示例请求：“林女士最近怎么样？帮我总结她的兴趣、成交阶段和主要顾虑。”

1. 使用 `search_3chat_customers`，传入用户提供的客户识别信息。
2. 唯一确定客户后保留返回的标准 `customer_id`。如果存在多个合理匹配，且下一步必须分析一位客户，请用户选择。
3. 使用 `search_3chat_customers_context` 查询该客户。根据分析需要返回对话实体和消息；只有用户需要诊断 AI 处理过程时才请求 `agent_logs`。
4. 区分 3Chat 返回的事实与模型推断，说明分析的时间范围，并在消息被截断或缺失时明确提示。
5. 输出简洁的客户简报，包括明确需求、兴趣、成交阶段证据、主要顾虑、未解决问题和建议动作。除非用户另行要求并确认，否则不发送消息。

## 2. 销售主管复盘近期对话

示例请求：“找出最近 30 天转过人工或还没有解决的对话，总结客户主要卡在哪里。”

1. 使用 `search_3chat_conversations`，设置时间范围以及工具支持的对话状态、转人工状态、解决状态或回复策略筛选条件。
2. 用户要求完整结果时持续分页。
3. 仅对需要聊天原文证据的对话，使用返回的 `customer_id` 或 `group_id` 查询相应上下文。
4. 按有证据支持的主题整理问题，例如价格、产品匹配度、时机、实施条件或信息缺失。
5. 说明样本数量、时间范围、排除条件和上下文缺失情况。如果结论是基于取回的数据由模型分析得出，不得声称这是服务端聚合分析结果。

## 3. 筛选并准备客户触达名单

示例请求：“找出最近 30 天咨询过但还没成交的高意向客户，准备一段有针对性的唤醒文案。”

1. 使用 `search_3chat_customers` 的列表查询模式，组合工具支持的标准字段、当前空间自定义字段和最后一次咨询时间条件。
2. 持续分页直到取得用户要求的完整名单。保留所有有效匹配，不要求用户从名单中确认唯一客户。
3. 需要验证客户意向、顾虑或个性化信息时，再查询客户上下文。
4. 向用户展示候选名单、筛选依据和拟发送文案，并区分返回数据与模型建议。
5. 到此停止，不执行发送。只有用户确认确切接收对象、发送账号或渠道、正文、附件和批量范围后才能发送。

## 4. 发送已确认的图片活动消息

示例请求：“把这张活动图片和介绍，群发给刚才这些匹配的客户。”

1. 复用刚才筛选结果中的标准客户 ID，并确认该名单仍是用户当前指定的范围。
2. 已有最终可直接下载的 HTTP/HTTPS 附件直链时直接使用；否则调用 `upload_3chat_attachment`，并复用完整的 `data.attachment` 对象。
3. 紧接发送前展示最终接收对象、发送账号或渠道、正文、附件和批量范围。
4. 用户明确确认后，单客户使用 `send_3chat_customer_message`，多客户使用 `send_3chat_customer_messages`，并遵守数量及幂等规则。
5. 批量发送返回 `job_id` 后，使用 `get_3chat_batch_send_status` 查询原任务，不重新提交批量任务。

## 5. 批量向指定客户发送消息

示例请求：“给最近 30 天咨询过产品但还没有成交的客户，群发一条活动邀请消息。”

1. 使用 `search_3chat_customers` 根据用户指定的标准字段、自定义字段和最后一次咨询时间筛选客户；需要完整名单时持续分页。
2. 保留查询结果中的标准 `customer_id`，展示客户名单、筛选条件和匹配数量，不要求用户从多人结果中选择唯一客户。
3. 根据客户信息和沟通上下文拟定消息。需要个性化内容时，可调用 `search_3chat_customers_context` 获取客户需求、兴趣和顾虑。
4. 发送前展示最终客户名单、发送账号或渠道、每位客户对应的消息正文、附件和批量范围，并取得用户明确确认。
5. 用户确认后调用 `send_3chat_customer_messages`。每个 `items[]` 应使用对应的 `customer_id`、消息内容、`confirmation_token` 和唯一的 `idempotency_key`。
6. 单次最多发送 100 位客户；为降低渠道限制和便于核对，建议每批先发送 1～3 位客户，再根据结果继续。
7. 工具返回 `job_id` 后，调用 `get_3chat_batch_send_status` 查询原任务，不得重新提交同一批量任务。
8. 任务结束后，根据统计字段和 `data.results[].success` 汇总成功与失败项，并使用单项错误字段解释失败原因。不得自动重新发送失败项。
9. `accepted`、`sent` 或 `COMPLETED` 只表示系统处理状态，不代表消息已被渠道送达或客户已读。

## 6. 查询批量发送任务

示例请求：“看看刚才的群发是否完成，并告诉我哪些客户发送失败。”

1. 使用原 `job_id` 调用 `get_3chat_batch_send_status`。
2. 状态为 `QUEUED` 或 `RUNNING` 时，按照规定的退避和运行时间限制查询同一个任务。
3. 任务进入终态后汇总统计字段，并逐项检查 `data.results[].success`。
4. 使用单项结构化错误字段解释失败原因，不自动重新发送失败项或结果不明确的项。
5. 不得把 `accepted`、`sent` 或 `COMPLETED` 表述成渠道确认送达或客户已读。
